# session-control

An orchestrator kit for Claude Code. One interactive session, the orchestrator, launches and manages headless `claude -p` worker sessions and reports their results.

- `CLAUDE.md` holds the orchestrator's instructions. The session reads it from its working directory.
- `mod/` is the session-control mod. It provides:
  - a side panel with the worker sessions, the queued work and the open points;
  - the worker tools `launch_worker`, `acknowledge_workers`, `retire_workers`, `close_worker` and `stop_worker`;
  - the bookkeeping tools `open_point`, `queue_task`, `record_decision` and `archive_decisions`;
  - the read-only inspection tools `list_sessions`, `read_result`, `worker_tail`, `session_writes`, `panel_snapshot` and `audit_state`;
  - a report check that sends a faulty orchestrator report back once;
  - notices that tell the orchestrator, one line each, what the poll finds worth acting on: an unregistered session, a stalled worker, a queued task whose blocker finished, an empty queue, a compliance check due, an old open point, housekeeping due and the orchestrator directory's git state (see Notices);
  - a guard that refuses hand edits of the helper files in the orchestrator's own session (see Helper-file guard).
- `model-complexity-matrix.md` is the lookup table for the model and effort of each worker. `CLAUDE.md` requires it at every launch.

## Requirements

- Linux or WSL with `/proc`.
- POSIX `sh` and the GNU tools the mod's shell scripts call: `jq`, `getconf`, `readlink`, `stat`, `sed`, `tr`, `cut`, `ls`, `head`, `tail`, `cat`, `sleep`, `mv`, `rm`, `mkdir`, `test`, and for the listing of `session_writes` without the Node helper `find` (with `-newermt` and `-printf`), `sort` and `awk`; for `stop_worker` without the Node helper `awk`, `kill` and GNU `date` (`+%s%3N`). They read process facts and edit the worker registry. On native Windows `stop_worker` runs the stock `taskkill.exe`.
- `git`, to clone the repository and, for workers, to create worktrees. `audit_state` reads the orchestrator directory's git state with it and says nothing about git where it is missing.
- A Claude Code build that supports mods. Tested on 2.1.292, 2.1.295 and 2.1.296.
- Python 3 (standard library only), only to run the self-tests `mod/tests/probe-selftest.py`. The mod itself runs no Python.
- Optional: Node.js 22 or newer, as `node` on the PATH or named by the `nodePath` option. With it the mod runs its file operations, and on Linux its process probe, through its own helper (`mod/helper/`, see Node helper); without it, or with the `helper` option set to `off`, the built-in `sh` (Linux) and PowerShell (Windows) operations run as before, with nothing to configure. The mod's hooks themselves run inside Claude Code's plugin sandbox, which has no Node.js API. Node.js 22 or newer is also what runs the helper's own tests.
- Optional: a licence picker command, set with the `licencePickCommand` option. `launch_worker` runs it for a fresh launch with `{need}` replaced by the headroom percent (a leading `~/` is expanded); it must print one absolute config directory on stdout and exit 0, or exit 3 when no licence has room. The command is split on blanks (no quoting; a path with spaces is not supported). Without the option a fresh worker gets no `CLAUDE_CONFIG_DIR` of its own and inherits the machine's default configuration: the orchestrator's `CLAUDE_CONFIG_DIR` when that is set, else `~/.claude` with the global config in `~/.claude.json`; the registry records that directory. `CLAUDE.md` leaves licence handling (headroom, reset times, event log) to the user-level instructions in `~/.claude/CLAUDE.md`. On a machine without licence tooling nothing needs configuring: every worker runs under the default config directory, `launch_worker` never refuses for licence room, and the licence steps in `CLAUDE.md` do not apply.

## Setup

1. Clone the repository. `CLAUDE.md` names the clone's parent directory as the workspaces directory: workers are launched in project directories below it.

   ```sh
   git clone git@github.com:llakeethur/session-control.git
   cd session-control
   ```

2. Start Claude Code from the clone's root with the mod loaded from its folder:

   ```sh
   claude --plugin-dir ./mod
   ```

   `CLAUDE.md` is picked up automatically from the working directory. The mod becomes active only in a directory whose `CLAUDE.md` starts with `# Role: Session Orchestrator`, unless the `orchestratorDir` option is set. Elsewhere `/session-control` answers that the directory is not an orchestrator directory and nothing else happens.

   This repository is not installed through the plugin marketplace. The mod is always loaded with `--plugin-dir`.

## First start

When the mod becomes active it creates each missing helper file from scratch and never overwrites an existing one:

| Path | Created as |
| --- | --- |
| `open-points.json` in the clone | an object with a short `_cleanup` text field and an empty `points` array |
| `task-queue.json` in the clone | an object with an empty `tasks` array |
| `agreed-decisions.md` in the clone | the heading `# Agreed decisions` |
| `open-points-archive.md` in the clone | the heading `# Open points archive` |
| `backups/` in the clone | an empty directory |
| `~/.claude/headless-sessions.json` | `[]` |
| `~/.claude/session-control/runs` | an empty directory |

The bookkeeping tools write a backup of the file they change into `backups/`, once per file, tool and day, before the first change of that day. `~/.claude/session-control/runs` receives each worker's result and error file and the log of retired registry entries (`cleared.jsonl`); a retire deletes the run files of a session it removes whose outcome was `clean`, only plain files directly in that directory (see `retire_workers`).

## Using it

`/session-control` shows or hides the side panel. The panel has three sections: Sessions, Queued work and Open points. The `[+]` icon in a section's header expands that section to the panel and keeps the other two as one-line headers with their own `[+]`, which expands that section directly (one section is expanded at a time); `[-]` returns to the three boxes, and opening a session's log returns to the log layout (sessions one third, log two thirds); an open log closes by itself, back to the three sections, when its session is no longer in the registry (a registry that cannot be read or parsed, or whose text is empty, keeps the log open). Tracking of runs, the completion handling and the report check run whether the panel is shown or not. The Sessions section lists every registry entry and, as an `orphan` row `(no entry) <cwd>`, each live headless `claude -p` process no entry claims; the licence daemon's own short runs are left out: a process whose prompt argument is `/usage` (the usage probe, `claude -p /usage --output-format json --no-session-persistence`) or `ok` (the token wake, `claude -p ok`), followed only by options, is not an orphan, while a worker whose prompt merely contains those words still is. The elapsed column reads `42s` under a minute, `5m12s` under an hour and `1h05m` from an hour up: a running worker counts from its entry's `started_at`, a finished one shows its run (`ended_at` less `started_at`), and an orphan or an entry without `started_at` shows the process age the probe read plus the time since that probe. While the panel is shown a one-second display tick recomputes that text and redraws, with no process started and no file read; it stops when the panel is hidden or closed, and the process probe keeps its own `pollSeconds` interval.

Worker completion: when a registered worker's process is gone, the mod classifies its result file and its error file (`clean`, `limit`, `login`, `killed`, `error` or `chatter`). `limit`, `login` and a memory kill come only from reliable signals: the API error status (429, 401), the result text and `errors` of a failed run (`is_error` true or a subtype other than `success`), a result file that is not JSON, and the error file; a result that is a success (`subtype` `success`, `is_error` false, no 429 or 401) is `clean` whatever the error file says, so a benign stderr line such as "usage limit reached, retrying" changes nothing, and the error file counts only when the result is not a success. The cost of that rule: a result file carrying `success` that is followed by a crash or an out-of-memory kill afterwards still reads as `clean`, because the successful result wins over the error file. A failed run's message may sit in `errors` (an array of strings) or in a string `error` field instead of `result`; both are read together for `limit`, `login` and a memory kill. The words of a normal report never count, since a report may quote those messages. The mod then shows a toast led by the notification type (`Session finished`, `Usage limit reached`, `Login needed`, `Session killed`, `Session failed`, `Session ended without a report`; the mod's other toasts lead with `Tracking problem`, `Write not atomic`, `Debug trace failed`, `Node helper` or the title of a notice, see Notices), then ` · ` and the message (a toast is one line of text: the engine draws no line break in it) and, with `completionWrites` on, merges the outcome into the worker's registry entry (it drops `pid`, sets `reported` to `false` and records the harvest time as `ended_at`, epoch seconds). The outcome reaches the model with the next task notification, as the note `session-control completions: <title>: <summary>`; the note's free text and the toast's (the entry's title, the outcome's summary drawn from the result file) go through the same redaction as the inspection tools and the notices first (decision mod-20), while the session id's first 8 characters, shown for an entry without a title, stay readable; the outcome stored in the registry entry is as before. For a `clean` outcome the mod also checks the final report: it must carry the output of `git status -sb` (its branch line) and of `git log --oneline @{u}..HEAD`, each with its exit code, as the worker prompts demand; the log's exit code must sit on its command line, in its output block or right after it, and commits are counted only in that block (it ends at a blank line, a code-fence end, an exit marker, the next `git` line or a heading). When one is missing, when that log exited non-zero or when it lists commits (unpushed work), the completion notice gets one more line, `<title>: report check: ...`; the check is tolerant of case, code fences, `$ ` prompts and `exit 0`, `exit=0`, `exit code: 0`, `exit status 0`, `exited 0`, `(exit 0)`, `→ 0`, `-> 0` or `rc=0`, and it is a note only: it never blocks anything and never changes the outcome or the toast. After a context compaction the next prompt carries a digest of the running workers and the open points.

### Tools

The tools are registered when the mod becomes active and are named `mcp__session-control__<tool>` to the model.

| Tool | What it does |
| --- | --- |
| `launch_worker` | Starts or resumes a headless `claude -p` worker as a background task, picks the licence for a fresh launch with the configured licence picker command (or uses the default config directory), finds its pid and session id and registers it in the worker registry. A fresh launch takes `dir`, `model`, `effort`, `title` and exactly one of `prompt_file` and `prompt`; optional are `need`, `timeout_minutes`, `resume_sid`, `section` and `rules` (see Launch parameters). |
| `acknowledge_workers` | Marks finished workers as acknowledged (`reported` true); `keep: true` also marks them as needed for a resume. |
| `retire_workers` | Removes finished, acknowledged, clean workers from the registry and appends the removed entries to `cleared.jsonl`. The optional `reviewed` input maps a session id (full, or the first 8 characters) to a non-empty reason the orchestrator wrote after reading the transcript and finding the stored outcome (`login`, `limit`, `killed`) wrong, or the work deliberately abandoned: for that session only the outcome check is skipped, and the entry's log line gets `reviewed_outcome` (the stored kind) and `reviewed_reason`; the answer says `Retired with review: <id> (was <kind>: <reason>)` and the debug trace's guard line carries both. A removed session whose outcome is `clean`, or whose retire was `reviewed`, loses its run files: its result file, its error file, the pid file beside the result file (`<result less .json>.pid`, the PowerShell route's) and the prompt file the mod wrote for it (the entry's `prompt_file`), each only when it is a regular file that sits directly in the runs directory: the path under the runs directory is one file name, with no `.` or `..` segment and no further folder (on Windows also no name with a colon, or ending in a dot or a blank), the file is no symbolic link (the path is looked at without following a link; on Windows no reparse point or junction either) and no directory or other non-file, it is no transcript (`.jsonl`) and no other registry entry names it in any field. A path plainly outside the runs directory, a transcript and a file another entry names are left alone without a word. A path with a `.` or `..` segment, one in a subfolder (so also one through a symbolic link to a folder inside the runs directory), a symbolic link and a non-file stay where they are and the answer names each: `(not deleted: <name>: <reason>; ...)` with the reasons `the path has . or .. segments`, `not directly in the runs folder`, `not a plain file name`, `is a symbolic link` and `is not a regular file`. The check of the file itself and the delete are one host operation, `removeRegularFile`: the Node helper's `removeFile` with `regularOnly` (a link or a non-file is refused with the fixed codes `IS_LINK` and `NOT_FILE`), and, when the helper is not there or a call fails, `REMOVE_REGULAR_SCRIPT` under `sh` on Linux and the `removeregular` operation of the file script on Windows, which make the same checks. The answer lists what went (`Run files deleted from <runs>: <id> (<file names>)`) and any file that would not go; the cleared-log line keeps the run's `cost_usd` and `duration_ms`, read from the result file before it is deleted (added to every removed entry's line whose result file holds them). The cleanup refuses nothing: a session the guards let go is removed whatever happens to its files. A resumed session's earlier runs left their own files, which the entry no longer names; `audit_state` lists them as run files no entry names. |
| `stop_worker` | `{session_id, reason?}` (the full id or its first 8 characters; `reason` at most 500 characters). Stops a registered worker that is alive and proves it dead: `CLAUDE.md` step 6 (Abort) by tool. Only a registry entry with a recorded pid is reached, never an orphan or an unregistered pid; it is refused (nothing signalled) when the entry has no pid (`refused: session <id> is not alive: its entry records no pid`), when the Abort check before fails (the sessions file `<config_dir>/sessions/<pid>.json` must name the session and its `procStart` must equal field 22 of `/proc/<pid>/stat`; on Windows its `startedAt` must fall in the probe's window around the process creation time: a dead or reused pid is never signalled), and when the pid is this session's own process or one of its ancestors. Then the host's `stopProcessTree` lists the worker's descendants before the first signal and stops the worker: Linux `SIGTERM`, a re-check every second for up to 10 seconds, `SIGKILL` to one still there, re-checks for up to 3 seconds; Windows `taskkill /PID <pid> /T`, the same re-checks, `taskkill /PID <pid> /T /F`; then each descendant still alive the same way. A process is signalled only while it keeps the start its listing found, and a zombie (it has ended; its `/proc` entry stays until its parent reaps it) is never signalled and is reported as exited. The waits run inside the stop's own processes (the helper or `STOP_SCRIPT` on Linux, one short `TREE_PS1` check per second on Windows), never on the engine's clock, so the hook's 10 s budget is not spent on them. Then the Abort check runs again, and it decides the result whatever the stop answered, also when the stop failed or the helper was cut off (its fallback is said in a `Note:` line). The answer is the proof: the pid and session, the reason, the Abort check before, the descendants listed, each signal with its time and exit code and each re-check, the descendants at the end, the Abort check after, the result (`dead`, `exited` as a zombie, or `STILL ALIVE ...: it is a live worker; report it as running, never as stopped`) and every surviving descendant (`still alive`). No registry field is written: the exit notification and the probe record the outcome as for any death. The trace keeps the session id, the pid and the counts (signals, survivors, whether it is dead after), never the reason or the title. |
| `close_worker` | `{session_ids, keep?, reviewed?}`. Acknowledges and retires in one call: exactly `acknowledge_workers` (with `keep`) followed by `retire_workers` (with `reviewed`), through their own code, with their refusals and their answers one after the other (`Acknowledged: ... Retired: ...`), and the run-file cleanup of the retire. `keep: true` only acknowledges and keeps; nothing is retired (a `reviewed` given then is said to be unused). Because the acknowledgement clears a `keep` mark, a kept session closed with `keep: false` is retired, as the two calls in a row would do. |
| `open_point` | Adds, answers, closes, holds or releases an entry of `open-points.json`. Settled entries older than 7 days move to `open-points-archive.md`. |
| `queue_task` | Adds, updates or removes a task of `task-queue.json`. |
| `record_decision` | Appends one numbered line to a section of `agreed-decisions.md`; the section is created when missing. An id that a line of `agreed-decisions.md` already starts with is refused, and so is one that a line of `agreed-decisions-archive.md` starts with, when that file exists (`decision <id> already exists in agreed-decisions-archive.md (an archived section's ids stay taken); choose another id`); an archive that is there but cannot be read refuses the write, since the id cannot be checked. |
| `archive_decisions` | `{sections}`: section headings of `agreed-decisions.md` without `## `, exactly as the file has them. Moves those whole sections (heading line to the next heading, the bytes as they are) into `agreed-decisions-archive.md`, created with the line `# Agreed decisions archive` when missing and only ever appended to, under one dated header line per call (`# Archived <date> from agreed-decisions.md`); the main file keeps one summary line per archived section, `- <heading> (ids <first> to <last>): archived <date> to agreed-decisions-archive.md`, under a `## Archived sections` heading it makes after the file's intro (`audit_state` never counts that section as stale). All or nothing: it refuses a `Standing` section (any heading that starts with Standing), `Archived sections` itself, an unknown or doubled heading, a heading named twice, and a section that a queue task not `done`, a running session (its title or name, or the section it was launched with) or an open point still names, by the whole heading (case aside), a decision id that holds a letter, or a branch, T-number or number of five digits or more of its heading, each as a whole word; the refusal names each task, session or point. The file is backed up into `backups/` once per day before the first change; the archive is written before the main file, each through a temporary file and a rename against the text read (Linux and Windows). |
| `list_sessions` | Read-only. `{include_finished?}` (default true). A count line, then one line per row of the panel's row builder: each registry entry with its title, session id, name, cwd, config dir, model, effort, status as the panel shows it, pid, elapsed text, outcome kind and summary, cost and keep mark; and each orphan (a live headless `claude -p` no entry claims, the licence daemon's probes left out) with its pid, cwd, config dir and age. `include_finished: false` leaves the finished rows out and says how many. |
| `read_result` | Read-only. `{session_id, max_chars?}` (default 12000, 500 to 50000). The worker's final report: the result file's `.result`; when that is chatter (the `chatter` label of the completion) or there is no result to read (no file, not JSON, no `.result`), the last assistant message of 200 characters or more of its transcript, a message's rows joined and a subagent's rows left out (a real report can sit under late notification chatter). It says the source used and why, the outcome label (and the registry's when it differs), cost, duration, turns, `is_error` and `subtype`, how many replacements the redaction made, and whether the report was cut (the head kept, the characters cut counted). Never the whole transcript. |
| `worker_tail` | Read-only. `{session_id, lines?}` (default 40, at most 200). The transcript's last lines summarised as the panel's log shows them, the seconds since the transcript was last written (the probe's, else the file's mtime) and whether the process is alive by the Abort check. |
| `session_writes` | Read-only. `{session_id}`. The files written under the session's cwd since its transcript's first timestamp (fractional seconds dropped; the entry's `started_at` when the transcript is over the read cap, which leaves out a resumed session's earlier runs), by mtime, newest first, at most 200 with the true count, `.git` and symbolic links left out (host `filesNewerThan`). Each path under the orchestrator directory is flagged `ORCHESTRATOR DIR`, the registry `REGISTRY`; then the transcript's own Write, Edit, MultiEdit and NotebookEdit calls on either, and the commands that name either. By mtime, a write of any other process in that tree shows too. |
| `panel_snapshot` | Read-only. `{}`. The text the panel shows as of its last poll, at 120 columns: the sessions rows (with the warning row when there is one), the open log when one is selected (its last 40 lines), the queued work and the open points (the selected one with its detail), from the panel's own state and row builders, as plain text. |
| `audit_state` | Read-only. `{}`. The end-of-unit audit of the helper files: a facts line (what the registry, queue, open points, `backups/`, the runs directory, `reports/`, `agreed-decisions.md` and git hold), then findings, each with its kind, subject, evidence and a suggested action, high first, at most 40 (the rest counted). High: a helper file that does not parse; a queue status other than exactly `queued`, `running` or `done`; a running task naming no live session (by session id, its first 8 characters or its session name); a queued task whose `waits_for` names a finished session or one retired (in `cleared.jsonl`). Medium: finished sessions not acknowledged or not harvested; done tasks still queued; sessions that can be retired (clean, acknowledged, not kept, named by no task that is not done); kept sessions idle for more than 6 hours; open points raised more than 7 days ago; tracked changes uncommitted in the orchestrator directory and how old; a branch other than the default with no worker alive (or a detached HEAD). Low: held open points; backups older than 2 days besides the newest of their kind (the kind is the name without its date); run files no registry entry names (the trace, `cleared.jsonl` and the mod's scripts aside); saved reports; decision sections whose unit no task, entry or open point names (by the branch, T-number or long number of the heading, else two of its words; `Standing` sections never). git runs as `git --no-optional-locks -C <dir>` with read commands only (`rev-parse`, `symbolic-ref`, `show-ref`, `status`), and nothing is said about git when it cannot start or the directory is no repository. |

`launch_worker` refuses, among other cases: a launch directory that is the orchestrator directory or `$HOME`; both or neither of `prompt` and `prompt_file`, or a blank `prompt`; a `section` the decisions file lacks; a missing or empty prompt file; a prompt that lacks a foreground wait, the `git status -sb` report line or the no-attribution instruction (a prompt that says "skill test" is exempt); a resume of a live session; a licence pick that exits 3 or prints nothing usable. A worker is started as `claude -p -n <name> --settings '{"crossSessionInbound":"accept"}' --dangerously-skip-permissions --output-format json` with `CLAUDE_CONFIG_DIR` set to the picked configuration directory and `CLAUDE_CODE_EFFORT_LEVEL` set to the requested effort, through the Bash tool; on native Windows with the `launchRoute` option at `powershell`, through the PowerShell tool instead (see PowerShell launch route).

Launch parameters:

- `prompt`: the prompt as text instead of `prompt_file` (exactly one of the two, else a refusal). The mod writes it to a prompt file of its own beside the run's result file, `<runs>/<session name>.prompt.md`, outside any repo, named by the launch's unique session name (`w-<slug>-<yyMMddHHmmss>`, with its `-2` suffix when that is taken), so two launches of one title in one second write two files (a resume keeps its entry's name, so its file adds the resume's time: `<runs>/<session name>-<yyMMddHHmmss>.prompt.md`), and launches with that path; the file is written only once the guards have passed, so a refused launch leaves nothing.
- `section`: a section heading of `agreed-decisions.md` (without `## `). Its lines, as the file holds them, are appended to the prompt after a blank line under `## Binding decisions (section <heading>)`; a heading the file lacks (or has twice), a decisions file that cannot be read, or a `prompt_file` that cannot be read is a refusal. With a `prompt_file`, the mod writes the extended copy as its own prompt file and leaves the given file as it is.
- `rules`: whether the standard rules block (`RULES_BLOCK` in `hooks/core.ts`) is appended when the prompt lacks one of the items the launch guard checks (a foreground wait, `git status -sb`, the no-attribution instruction). The block carries the worker-prompt items of `CLAUDE.md`: no AI attribution trailer and no agent mentioned in anything written; no human answers during the run, look up, then a documented default, never for a sign-off item; never read, print or pass a credential; long runs with `run_in_background: true`, an explicit timeout, foreground waits under ten minutes in `until` loops, never ending the turn while a run is live; the report with `git status -sb` and `git log --oneline @{u}..HEAD`, each followed by its exit code. A prompt that already carries the guard's items, or a skill test, gets no block, so it never gets a second copy. Default: true when the mod writes the prompt (`prompt` given, or a `section`), false for a `prompt_file` given alone, which is launched as it is and refused when it lacks the items, as before.
- A resume (`resume_sid`) may leave out `dir`, `model`, `effort` and `title`: they are taken from the registry entry (its `cwd`, `model`, `effort`, `title`); a value given wins, and the answer ends with `From the entry: <fields>.`. The resume runs under the entry's config directory as before.

Without `prompt`, `section` and `rules`, a launch runs the same command, answers the same text and writes the same registry entry as before these parameters existed. With them, the answer ends with `Prompt: <path> (written by the mod; ...)`, saying what was appended, and the entry records `prompt_file` (the mod's prompt file, which a retire deletes) and `section`. The debug trace records `rules` and a `launch.prompt` line (the prompt file's path and length, whether it was inline and what was appended), never the prompt text or the section heading.

Inbox: every worker gets a session name with `-n` and accepts messages from other sessions on the machine (`crossSessionInbound` set to `accept` through `--settings`), so the orchestrator can send a running worker a message by its name. The name is `w-`, the slug of the title cut to 24 characters, and the launch time in UTC as `yyMMddHHmmss` (for example `w-fix-the-parser-261010143117`): letters, digits and dashes, at most 39 characters before a uniqueness suffix; a name already in the registry or given out by the same session gets `-2`, `-3` and so on. The uniqueness check covers only the registry and the session's own names, so two orchestrator sessions starting workers with the same title in the same second can still get the same name. A resume passes the same two flags and keeps the entry's name, so a session answers to one name across resumes; an entry without a name (launched before names existed) gets a fresh one. The worker's exit is still detected through the background task's notification.

Registry entry: `launch_worker` records `title`, `pid`, `session_id`, `name`, `socket_path`, `config_dir`, `cwd`, `model`, `effort`, `result_file`, `err_file` and `started_at`, the time the launch started the run in epoch seconds, and, when the mod wrote the prompt, `prompt_file` and the `section` appended; a resume sets the new run's `started_at` and drops the previous run's `ended_at`. Entries written before these two fields existed stay valid without them. `name` and `socket_path` come from the worker's sessions file `<config_dir>/sessions/<pid>.json` (`name` and `messagingSocketPath`), read with the session id; `name` falls back to the name the launch passed. A claude that writes no socket (an older version) gives an entry without `socket_path`, and a resume then writes `socket_path: null` so the previous run's socket is not kept. The socket is valid only while the pid lives. The launch answer names both.

The six inspection tools change nothing: they write no file and start no process but the process probe, a transcript tail, the listing of `session_writes` and the git reads of `audit_state` (on Windows without Node a PowerShell script is written to the runs directory before its first run, as every PowerShell operation of the mod does). A session id is the full id or its first 8 characters; an unknown one, or one two entries share, is a refusal that says so. Each answer is plain text of a bounded size (at most 60000 characters, the cut said). Every free text read from the registry, a result file, a transcript or a helper file goes through the debug trace's redaction (`redact` in `hooks/trace.ts`: keys, tokens, JWT parts, `key=value` and `--flag value` secrets, URL user info, curl's `-u user:pass`, `--user user:pass` and `--user=user:pass`, also with a quoted password that holds blanks (`-u 'alice:s3cret pw'`) (not docker's numeric `-u 1000:1000`, not a value whose second part starts with a slash or, quoted, a blank; known over-redaction: any other value of the form `name:name` after `-u` or `--user` cannot be told from a credential and goes, whatever the command, so `--user www-data:www-data`, `docker run -u root:root`, `sort -u a:b`, `echo -u foo:bar` and `git push -u origin:main` show `[redacted]` too), long runs of letters and digits become `[redacted]`; a UUID and a plain path stay), so a long hex string shows as `[redacted]`. The exception is a git object id: a lower-case hex string of exactly 40 or 64 digits that is no part of a longer run of letters and digits, on a line that is evidently git, is shown as it is, so `origin 7ebdad1d... refs/heads/main` of a `git ls-remote` reads whole. A line is evidently git when it has `refs/`, `commit ` (the word and a blank), `HEAD`, a range of two hex ids (`a..b`, `a...b`), `git ls-remote`, `git log`, `git rev-parse` or `sha` as a word (`sha`, `sha1`, `sha256`), or when the id starts a `git log --oneline` row (the id, a blank, a subject). Each line decides for itself, so an id alone on its line (the output of `git rev-parse HEAD`) is redacted; so is an id right after `key`, `token`, `secret`, `password`, `auth` or `credential` or after `=` or `:` (`sha: <id>` and `sha=<id>` too), an id of any other length (32 to 39, 41 to 63, over 64), one in upper case and one inside a longer run. The debug trace uses the same function. File names are redacted as paths are, so a dated name reads whole. The mod's own identifiers are exempt: a session id of the UUID form and a session name of exactly the form a launch generates are shown as they are wherever a tool names a session (`list_sessions`, the heading of `read_result`, `worker_tail` and `session_writes`, an ambiguous-id refusal). That form is `w-`, the slug (lower-case letters, digits and dashes, maybe empty), `-`, twelve digits (`yyMMddHHmmss`) and an optional `-<number>` suffix, at most 64 characters (`GENERATED_NAME` in `hooks/core.ts`); a resumed session keeps its entry's name, which has that form. Any other value in those fields is free text and redacted: a name without the twelve-digit stamp, one with an upper-case letter or a blank, one of more than 64 characters, and a secret-shaped lower-case string behind `w-` among them. Terminal control sequences are dropped. No tool reads `.credentials.json` or `~/.claude.json`. The trace records each call's named fields and the answer's length only (`resultChars`), never its text.

`acknowledge_workers` and `retire_workers` refuse a worker whose process is alive. `retire_workers` also refuses a worker that is marked keep, whose outcome is not `clean` (unless `reviewed` gives a reason for it) or that a queued or running task names. A `reviewed` entry never lifts the other refusals (a live, kept, unclassified, queue-named or unknown session), and one without a reason, or naming a session that is not in `session_ids`, is refused.

### Notices

The orchestrator is a model session: it hears of a worker's exit through the harness and of everything else only when it looks. The mod already knows more at each poll, so it tells the orchestrator the useful part, sparingly (decisions win-20, win-21, win-22, win-27, win-36, win-38 and mod-3). Each notice is:

1. one line the model reads, `session-control notice: <kind>: <message>`, kept until the next prompt of any origin (a prompt the user types, a task notification, a peer message) and handed to the model as that prompt's additional context, the lines joined by line breaks, after the `session-control completions: ...` note when there is one (at most 30 lines wait: past that the first 29 stay and the last says `session-control notice: more: N further notices not shown; run list_sessions and audit_state`, its count growing with each notice that does not fit, so nothing is dropped silently); under the hold rule a notification-only turn answers with one line, so a notice is one line too;
2. a toast, `<title> · <message>` (one line), the title by kind as in the table; at most 3 per source in one refresh (the poll's notices, the notices of all the harvests of that refresh together, a queue change's), the rest told by one toast at the end of the refresh, `More notices · N more notices: see the next prompt` (decision mod-20; a refresh that harvests and polls can thus show up to 6 notice toasts and the one summary);
3. with the debug trace on, a `notice` line with the kind and the notice's ids and counts (a pid, a session id, a task or open point id, how many), never its text, a title, a section heading or a path.

Of the orphans that come due at one poll, the first 5 are told one notice each and the rest in one notice, `orphan: N more unregistered sessions: <the first 10 pids> and M not listed; list_sessions shows each; raise an open point naming them`; every one of them is marked told in the debounce state, so none is told again.

No notice starts a turn: the mod never submits a prompt of its own, so an idle orchestrator reads them with its next prompt, and sees the toast at once. The option `notices` (`on` by default) at `off` turns every one of them off; the completion notes and their toasts stay.

| Kind | Toast title | When | Debounce | Line (after `session-control notice: <kind>: `) |
| --- | --- | --- | --- | --- |
| `orphan` | `Unregistered session` | a live headless `claude -p` no registry entry claims (the predicate of the orphan rows, `orphanProcs` in `hooks/core.ts`: the licence daemon's probes left out), seen unclaimed by the poll for 30 seconds; never the orchestrator's own process (an orphan whose sessions file `<config dir>/sessions/<pid>.json` names this session's id) | once per pid; a pid claimed or gone is forgotten, so a launch registered within the 30 seconds is never told | `pid 5555 is a live headless claude no registry entry claims (cwd /w/other, config dir /home/u/.claude, age 10m00s, unclaimed 30s, session <id its sessions file names>); raise an open point naming it` |
| `stall` | `Session stalled` | a registered worker whose pid is alive by the Abort check and whose transcript the probe reports unwritten for 15 minutes | once per episode: the transcript mtime it was told at is kept, a newer mtime re-arms it; a session no longer alive is forgotten | `worker "<title>" (session <name, else the id's first 8 characters>) is alive but its transcript has not been written for 16 min; look at it with worker_tail` |
| `queue-ready` | `Queued task ready` | a completion harvested (the existing merge): each task with status `queued` whose `waits_for` names that session (its full id, its first 8 characters or its session name) | once per task and run (a resume that finishes again under a new pid is told again) | `queued task <id> waited for <session>, which finished` |
| `unit-complete` | `Queue empty` | after a `queue_task` change or a harvest, no task is `queued` or `running` | once, until a poll or a change finds a task queued or running again | `queue empty: run audit_state and report` |
| `compliance-due` | `Compliance check due` | a harvested completion with outcome `clean` whose entry records the decisions `section` it was launched with | once per session | `compliance check due for section <heading> (session <name>)` |
| `open-point-age` | `Open point waiting` | an open, not held point older than 24 hours: its `raised` date gives the day only, so its age counts from the earlier of the end of that day and the first poll that saw it open | once per point and local day | `open point <id> (raised <date>) is still open: <title>` |
| `retire-due` | `Housekeeping due` | from the poll's timer, the findings of `audit_state` itself (`auditFindings` in `hooks/audit.ts`) over the registry, the probe, the queue and `cleared.jsonl`: sessions that can be retired (clean, acknowledged, not kept, named by no task not done), kept sessions idle more than 6 hours, and stale queue tasks (a status other than exactly `queued`, `running` or `done`; running with no live session; queued waiting on a finished or retired session; done tasks still listed) | at most once per hour; while it is due the findings are worked out at most once a minute | `1 finished session can be retired (33333333); 1 kept session idle over 6 hours (44444444); 3 queue tasks look stale (q-blocked, q-run, q-done): run audit_state` (three ids per group, then `and N more`) |
| `repo-state` | `Repository state` | from the poll's timer with no worker alive: the git reads of `audit_state` (`gitState` in `register.tsx`, `gitFindings` in `hooks/audit.ts`) show the orchestrator directory on a branch other than the default (or a detached HEAD), or tracked changes whose oldest is 30 minutes old or more; silent when git is missing or the directory is no repository | git runs at most once per hour, and not at all while a worker is alive; the notice comes with that check | `the orchestrator directory is on branch feature/x, not the default main and has 1 tracked file uncommitted, the oldest change 1h01m old, with no worker alive: run audit_state` |

The thresholds are constants in `hooks/notices.ts`, not options: `ORPHAN_GRACE_SEC` 30, `STALL_SEC` 900, `OPEN_POINT_AGE_SEC` 86400, `RETIRE_EVERY_SEC` 3600, `RETIRE_CHECK_SEC` 60, `REPO_EVERY_SEC` 3600, `REPO_CHANGE_AGE_SEC` 1800, `NOTICE_IDS_SHOWN` 3, `PENDING_NOTICES_MAX` 30, `TOASTS_PER_PASS` 3, `ORPHANS_SHOWN` 5, `ORPHAN_PIDS_LISTED` 10; the 6 hours of a kept session are `KEPT_MAX_SEC` of `hooks/audit.ts`. Every time rule reads the mod's clock (`$.clock`), which the tests drive with the mocked clock. The notices start no process of their own beyond what the poll runs: the probe, the queue, the open points and the registry are the poll's own reads; an orphan's sessions file is read once, when its 30 seconds are up; `cleared.jsonl` is read only while retire-due is due; git runs only for repo-state, at most once per hour. The notices of what every refresh reads (orphan, stall, open-point-age, and the re-arming of unit-complete) also run when the board turns on (the session's start, `/session-control`) and after a tool's own refresh; retire-due and repo-state come only from the poll's timer, from its first tick on.

Their debounce state is kept in the mod's own store (`$.store`, a JSON file of the engine's under the user's configuration directory, kept between sessions and hot reloads) under one key per orchestrator directory, `notices:<directory>`, so a reload of the mod, or a new session in the same directory, tells nothing again; it is pruned at each poll (a pid, session, task or point that is gone leaves it), and the key of an orchestrator directory that no longer exists is dropped at the first notice pass of a load. A store that cannot be read or written keeps the state in memory for the load (one `error` trace line, `notices.store`).

A registry the poll cannot use is never taken for an empty one (decision mod-20): when the registry file is missing or cannot be read, is empty or only whitespace, or does not parse as a JSON array (`isRegistrySound` in `hooks/notices.ts`), that poll skips every notice step that reads the registry, their pruning included: orphan (no orphan timer starts, none is forgotten), stall (a stall told stays told), the pruning of the queue-ready and compliance-due state (those two come from a harvest, which needs registry entries), retire-due and repo-state. Their state stays as it was and nothing of theirs fires, so a registry that flaps between readable and not tells a stalled worker once, and a registered live worker never becomes an orphan notice. Open-point-age and the re-arming of unit-complete, which read only the points and the queue, still run, except after a registry that does not parse: that refresh stops at the panel's warning, as before, and no notice step runs. A registry that reads as `[]` is a sound, empty registry: a live headless claude it does not claim is an orphan as before.

Verified live on 2.1.296 (Linux, WSL 2) with an interactive haiku orchestrator in tmux on a scratch directory (`pollSeconds` 2): every kind was shown as a toast and reached the model as one line with the next typed prompt, which the model repeated verbatim (two throwaway `sleep` processes stood in for registered workers, one with a transcript 20 minutes old; a real `claude -p` sleeper was the orphan); `/session-control` raised no prompt and drained nothing; a new session in the same directory and a hot reload of the mod told nothing again. The 24-hour, hourly and 15-minute rules beyond what that run reached are covered by the mocked-clock tests.

### Helper-file guard

In the orchestrator directory's own session (the session started there, with the board on) the model may not edit the helper files by hand (decision mod-2): a `tool.call` hook on `Edit`, `Write`, `MultiEdit`, `NotebookEdit`, `Bash` and `PowerShell` refuses such a call with the tool to use instead, for example:

```
session-control: refused by the helper-file guard: task-queue.json is a helper file the mod's tools write; in this session it changes only through the session-control tool queue_task, never by hand (Bash: sed -i). Use queue_task instead. Reading it is fine (cat, head, tail, grep, jq without an output redirection); CLAUDE.md, backups/ and reports/ stay editable by hand.
```

The protected files are one list, `HELPER_FILES` in `mod/hooks/guard.ts`, each with its place and the tools that write it:

| File | Place | Written by | The refusal names |
| --- | --- | --- | --- |
| `open-points.json` | orchestrator directory | `open_point` | `open_point` |
| `open-points-archive.md` | orchestrator directory | `open_point` | `open_point` |
| `task-queue.json` | orchestrator directory | `queue_task` | `queue_task` |
| `agreed-decisions.md` | orchestrator directory | `record_decision`, `archive_decisions` | `record_decision or archive_decisions` |
| `agreed-decisions-archive.md` | orchestrator directory | `archive_decisions` | `record_decision or archive_decisions` |
| the registry (`registryPath`) | its own path | `launch_worker`, `acknowledge_workers`, `retire_workers`, `close_worker` | those four |
| `cleared.jsonl` | runs directory | `retire_workers`, `close_worker` | `launch_worker`, `acknowledge_workers`, `retire_workers` or `close_worker` |

Not protected, and listed with their reasons in `UNGUARDED_FILES` of the same file: `backups/` (the daily copies the tools make), the temporary sibling of an atomic write, a launch's run files in the runs directory (result, error, pid and the prompt file the mod writes), the trace, the mod's own PowerShell scripts and a Windows append's staging file. `CLAUDE.md`, `reports/` and every other file are not checked at all. `mod/tests/guard.test.ts` runs every registered tool on a mock machine and fails when a tool writes a file that is in neither list, or when a registered tool has no scenario there: a tool that writes a new file cannot be added without saying in the list what that file is.

How a call is judged:
- `Edit`, `Write`, `MultiEdit` and `NotebookEdit` by the path they write: made absolute against the session's directory, `.` and `..` folded, and resolved through its symbolic links by the host (`$.fs.stat` with `resolve`; a file not there yet by its folder), compared with each protected file the same two ways; on Windows in any case, with `\` or `/`, and in Git Bash's `/c/...` form.
- `Bash` and `PowerShell` by the command's text: a protected file named (by its base name, or a path ending in it, in any case) together with a construct that writes it: an output redirection to it (`>`, `>>`, `>|`, `&>`, a descriptor before them; a duplication such as `2>&1` writes nothing), or a redirection to a variable in a command that names it; `tee`, `mv`, `cp`, `rm`, `unlink`, `truncate`, `shred`, `install`, `ln`, `rsync`, `sponge`, `patch`, `touch` and the editors; `sed -i`, `perl -i`, `ruby -i`, `awk -i inplace`, `yq -i`; `dd of=`; `git checkout`, `restore`, `rm`, `mv`, `apply`; `find` with `-delete` or `-exec`; a Python, Node, Perl, Ruby, PHP or awk one-liner that names it and writes (an open for writing, `write`, `rename`, `unlink`, `shutil`, `os.replace` and the like); PowerShell's `Set-Content`, `Out-File`, `Add-Content`, `Remove-Item`, `Move-Item`, `Copy-Item`, `Rename-Item`, `New-Item`, `Clear-Content`, `Tee-Object` and their aliases in any case, and a .NET `[IO.File]::Write...`, `Append...`, `Delete`, `Move`, `Copy` or `Replace` call; `cmd.exe`'s `del`, `copy`, `move`, `ren`; and each of these inside `sh -c`, `bash -c`, `eval`, `cmd /c` and `powershell -Command` or `pwsh -c`. Reading commands run: `cat`, `head`, `tail`, `grep`, `jq` without an output redirection (with one to another file too), `wc`, `ls`, `stat`, `sha256sum`, `diff`, `sed -n`, `Get-Content`, `Select-String`.

The command check is a guard against slips, not a sandbox. It cannot see what the text does not say: a glob (`task-*.json`), a name built at run time across segments, a name read from a file or from another command's output (`ls | xargs rm`), a script file it runs (`python3 fix.py`), a PowerShell `-EncodedCommand`, a link or alias to a helper file that already exists (a `sed -i q` names only `q`), a rename of a parent folder, and a writer it does not list. It can refuse a harmless command that names a helper file beside a writing command (`cp task-queue.json /tmp/copy`), or a file elsewhere with a helper file's name: read a helper file with `cat`, `head`, `grep` or `jq` instead.

The mod's own tools are never refused: they write through `$.fs` and the helper, not through a tool call, and a tool call the mod makes itself (the launch's `Bash`) passes untouched. Outside the orchestrator directory's own session (another directory, also with the `orchestratorDir` option set, or a session started elsewhere that turned the board on with `/session-control`) the guard does nothing. When the guard's own reads fail, or the call is a re-entry, its `.catch` decides from the call's text alone, without resolving links. A refusal is a `guard` trace line with the tool and the file's name, never the command or the path written.

`sh mod/tests/e2e-stop.sh` runs `stop_worker` in the real `claude`: a haiku orchestrator (capped at `--max-budget-usd 0.25`) launches a haiku worker that runs foreground `sleep 20` calls, waits until the scratch registry shows it alive with a `sleep` below it (its tree is then recorded from `/proc` with each start), calls `stop_worker` on it, on an unknown id and on a finished entry; it checks the proof text, that every signal went to a process of the recorded tree, that `/proc` shows the worker and its whole tree gone, that a bystander `sleep` of the script and every other `claude` process alive before are untouched, and the two refusals. `KEEP_OUT=<dir>` keeps the outputs and the recorded tree.

`sh mod/tests/e2e-guard.sh` runs the helper-file guard in the real `claude`: a haiku orchestrator in a scratch orchestrator directory is told to `Write` over `open-points.json`, run `sed -i` on `task-queue.json`, run `cat` and `jq` on it, `Read` and `Edit` its `CLAUDE.md` and call `open_point add`; the first two must be refused with the guard's text, the rest must run, and on disk `task-queue.json` must be byte for byte as seeded, `open-points.json` must hold the tool's point and `CLAUDE.md` the edit.

`sh mod/tests/e2e-write-tools.sh` runs the write-side tools in the real `claude`: a haiku orchestrator (capped at `--max-budget-usd 0.25`) launches one haiku worker ("reply PONG") through `launch_worker` with an inline `prompt`, a `section` of a scratch decisions file and the default rules, waits for its outcome in the foreground (a copy of the prompt file the mod wrote and the registry entry are taken at that moment), closes it with `close_worker`, retires three hostile registry entries with `retire_workers` (a result file that is a symbolic link out of the runs folder, one named through a `..` path, one named through a symbolic link to a folder), calls `archive_decisions` on a section a queue task names (refused) and then on the free one (archived), and calls `list_sessions`. It checks each output against the seeded data, that the prompt file starts with the prompt given and carries the section's lines and one rules block, that the retire deleted the result, error and prompt files (the worker's transcript stays) and kept cost and duration in `cleared.jsonl`, that the hostile entries are named as not deleted and every file and link they lead to is still there, the archive and the decisions file byte for byte, the backup, and that the trace holds no prompt or section text. Both transcripts stay under the default configuration; the scratch directory is removed. `KEEP_OUT=<dir>` keeps the outputs, the prompt copy and the files.

After a change to the mod, run the validation and the tests before relying on it.

## Host adapters

Everything the mod does that differs per operating system, or needs a process, goes through one interface, `Host` in `mod/hooks/host.ts`, with two adapters: `host-posix.ts` (Linux and WSL: `sh`, `mv`, `rm`, `tail`, `mkdir`, `sleep`, `/proc`) and `host-windows.ts` (native Windows: Windows PowerShell 5.1 scripts run with `-File`, paths in the `C:/...` form). `selectHost` in `host.ts` is the one platform choice: `OS=Windows_NT` with a drive-letter `USERPROFILE` takes the Windows adapter, anything else the Linux one. `register.tsx` calls it once per load and never branches on the platform itself. Each adapter's scripts sit in its own file; operations both do alike with `$.fs` and plain TypeScript are in `host-shared.ts`.

An adapter never holds `$` (the validator follows `$` only into functions of `register.tsx`): it gets a `HostPort`, the engine facilities `register.tsx` builds over the hook's `$` (`run` and `write`, traced as before; `read`, `exists`, `stat`, `now`, `sleep`, `env` for `HOME`, `USERPROFILE` and `SystemRoot`; the runs directory; `traceError`; `noteDirectWrite`, the once-per-load toast; `noteHelper`, the Node helper's detection and fallbacks). With the `helper` option at `auto` the chosen adapter is wrapped by `withHelper` (`host-helper.ts`, see Node helper).

## Node helper

`mod/helper/host.mjs` (with `protocol.mjs`, `ops.mjs`, `files.mjs` and `linux.mjs`) does the host operations the engine's `$.fs` lacks in one Node.js process per call: Node 22 or newer, standard library only, no build step. The mod finds it under its own folder (`$.plugin.root`). Its protocol:

1. The mod runs `node <plugin>/helper/host.mjs <op>` by argv, no shell, with one JSON request on stdin.
2. The helper prints one JSON object: `{"ok":true,...}` with the answer's fields, or `{"ok":false,"code":"<CODE>"}`, and exits 0 or 1.
3. Codes are fixed words (`BAD_OP`, `BAD_REQUEST`, `TOO_LARGE`, `UNSUPPORTED`, `NOT_FOUND`, `ACCESS`, `BUSY`, `EXISTS`, `IS_DIR`, `NOT_DIR`, `NO_SPACE`, `READ_ONLY`, `CROSS_DEVICE`, `IO`, `INTERNAL`): no Node error message, path or file content is ever part of an answer.
4. Operations: `processTree` and `stopProcesses` (Linux only, like the probe, and never in a batch: the tree and the stop of `stop_worker`, printed as `TREE_SCRIPT` and `STOP_SCRIPT` print them; signals by `process.kill`, the waits inside the helper; always the live `/proc`, never the probe's test tree: `SC_HELPER_PROC_ROOT` is ignored here, since a fake tree's pids would be signalled on the real machine), `probe` (Linux: `/proc` read natively, printed as `PROBE_SCRIPT` prints it, `CLAUDE_CONFIG_DIR` the only value taken from a process environment, `procStart` and `sessionId` the only fields taken from a sessions file), `writeAtomic`, `renameOver`, `removeFile` (`{path, regularOnly?}`: with `regularOnly` a symbolic link, or on Windows a junction, is refused with `IS_LINK` and a non-file with `NOT_FILE`, by `lstat`, and nothing is removed), `append` (one write on an append descriptor), `tail` (the last 600 lines from the end of the file, each cut to 20000 characters, or the lines and width asked, the answer kept under the engine's 4 MiB output cap by leaving out the oldest lines), `rotate`, `filesNewerThan` (read-only: `{dir, since, max}` answers `{files: [{path, mtimeMs}], total}`, a walk by `lstat` that never follows a symbolic link or, on Windows, a junction out of the tree, passes over a folder it cannot read and never enters `.git`).
5. `batch` runs a list of file operations in order in one process and stops at the first failure, answering its position.

`withHelper` in `mod/hooks/host-helper.ts` puts the helper in front of the chosen adapter. For `stopProcessTree` on Linux it lists the tree with `processTree` (a failure there leaves the whole stop to the adapter, which lists itself) and stops it with `stopProcesses` (timeout 45 s); a stop that fails falls back to `STOP_SCRIPT` over the same listing, which signals only a process that still has its listed start, and the report's `Note:` says so (after a timeout also that signals the helper sent before it was cut off are not in the record); the Abort check after the stop decides what `stop_worker` says. On Windows the stop stays on `TREE_PS1` and `taskkill.exe` (Node's standard library cannot list processes). Node is looked for at the first operation that needs it (`node --version`, untraced): without Node, or with one older than 22, the adapter's own operations run, with a `helper` trace line and no error. While no usable Node was found, the first helper-needing operation 10 minutes or more after the last lookup looks again, so a Node installed meanwhile is taken without a reload; operations at the same moment share one lookup, and a Node once found stays for the load. The `helper` trace line is written once per change of state (not found, too old, found), not at every lookup. A call that fails (Node cannot start or times out, its output is cut, is not one JSON object, or answers `ok:false`) falls back to the adapter's own operation for that call: the trace gets a `helper.fallback` line with the operation and the code, and the first fallback of the load raises one toast (`helper fallback: <op>`). The one exception is an append (a log line, or the trace's own rotate-and-append batch) that timed out: the helper may have written it already, so it is not made again. Its `helper.fallback` line carries `isRepeated: false`, the toast reads `helper fallback: append (timed out, not repeated)`, and the lines may be missing from the log but are never in it twice. Every other failure of an append (Node not starting, an exit code with no answer, an answer that is not JSON, `ok:false`) means nothing was written, and the adapter appends. On Windows the process probe stays `PROBE_PS1` (Node's standard library cannot list processes) and a transcript under the read cap is still read in the engine; the helper replaces the PowerShell file script. The trace's own write goes as one batch (rotation, then append). The built-in adapters stay as the fallback.

Cost measured on the machines it targets (medians: of 100 runs on Linux; on Windows of 20 single operations, 5 batches and one tail, timed from WSL through interop):

| Machine | Operation | Helper | Built-in |
| --- | --- | --- | --- |
| Linux (WSL 2, Node 24.14.0) | process probe, 2 arguments | 31.1 ms (27.6 ms in an earlier run) | 32.9 ms `sh` `PROBE_SCRIPT` (23.7 ms in the earlier run) |
| Linux | registry write | 39.0 ms `writeAtomic` (with fsync) | 1.7 ms for the one `mv -f`, plus the engine's own write of the temp file (not timed) |
| Linux | append | 25.9 ms | 1.3 ms (`sh` `APPEND_SCRIPT`) |
| Linux | bare `node -e 0` | 14.8 ms | |
| Windows (Node 22.10.0) | one file operation | 90 ms | 233 ms (PowerShell file script) |
| Windows | a batch of 20 file operations | 122 ms per batch | |
| Windows | tail of a 3.1 MB file | 100 ms | |

On Linux the helper costs one Node start per call where the built-in operations cost a few milliseconds (the probe is about even); on Windows it is about 2.5 times faster per operation than PowerShell, and a batch costs one Node start for all of its operations.

## PowerShell launch route

On native Windows the engine offers its Bash tool only when it finds Git Bash. With the `launchRoute` option at `powershell`, `launch_worker` starts the worker through the engine's PowerShell tool instead (PowerShell 7 or Windows PowerShell 5.1, whichever the tool runs; the engine offers that tool by default only when it does not find Git Bash, otherwise with `CLAUDE_CODE_USE_POWERSHELL_TOOL=1`). The default, `bash`, is the route described above, unchanged; on Linux and WSL the option changes nothing. `hooks/host-powershell.ts` builds the command; for a fresh launch with a picked config directory it reads:

```powershell
$env:PSModulePath = "$PSHOME\Modules"
$ErrorActionPreference = 'Stop'
$env:CLAUDE_CODE_EFFORT_LEVEL = 'high'
$env:CLAUDE_CONFIG_DIR = 'C:/Users/u/.claude/lic-b'
$exe = (Get-Command claude.exe -ErrorAction Stop).Source
$p = Start-Process -FilePath $exe -ArgumentList '-p --model opus -n w-fix-the-parser-261010143117 --settings "{\"crossSessionInbound\":\"accept\"}" --dangerously-skip-permissions --output-format json' -WorkingDirectory 'C:/work/my project' -RedirectStandardInput 'C:/Users/u/scratch/prompt.md' -RedirectStandardOutput 'C:/Users/u/.claude/session-control/runs/20261010143117-fix-the-parser.json' -RedirectStandardError 'C:/Users/u/.claude/session-control/runs/20261010143117-fix-the-parser.err' -NoNewWindow -PassThru
$null = $p.Handle
Set-Content -LiteralPath 'C:/Users/u/.claude/session-control/runs/20261010143117-fix-the-parser.pid' -Value $p.Id -Encoding Ascii
$p.WaitForExit()
exit $p.ExitCode
```

- **Flags**: those of the Bash route, in its order (`--resume <session id>` right after the model for a resume), with no prompt argument: the prompt reaches `claude.exe` on standard input from the prompt file, so it never meets the command-line length limit and no PowerShell encoding touches it. The result and error files are `claude.exe`'s own standard output and error (Start-Process's redirections: the bytes go through as written). `CLAUDE_CONFIG_DIR` is set only when the worker does not inherit the config directory, as on the Bash route.
- **Quoting**: Windows PowerShell 5.1 joins Start-Process's argument list with blanks and quotes nothing, so the arguments go as one string, each quoted by the C runtime's command-line rules that `claude.exe` parses with: a plain word stays as it is (so the probe still finds `--model opus`), anything with a blank or a double quote goes in double quotes with its quotes, and the backslashes before them, escaped. The `--settings` JSON thus arrives as one argument under 5.1 and 7 alike. Every value then sits in a PowerShell literal that keeps the whole command in printable ASCII: single-quoted with its quotes doubled, or, for a value with other characters (a user folder `José`), double-quoted with `$([char]0x....)` for each of them, so the command reads the same whatever encoding the tool hands it on in.
- **Wildcards**: Start-Process reads `-WorkingDirectory` and its redirection paths as wildcard patterns. The launch directory is escaped (each `[`, `]`, `*`, `?` and backtick behind a backtick), which both versions read back as the path. No spelling of a redirection path with `[`, `]` or a backtick reaches both versions (plain, the pattern finds no file; escaped, PowerShell 7 looks for the backticks themselves, and 5.1 does for standard input), so on this route a prompt file or runs directory holding one of them is refused before anything runs, with a message naming the path.
- **Refusal without the tool**: when the session has no PowerShell tool the launch is refused (`the worker could not be started through the PowerShell tool (...); nothing was launched.`) with the hint to start the orchestrator with `CLAUDE_CODE_USE_POWERSHELL_TOOL=1` or to set the option back to `bash`; there is no silent fall back to the Bash tool.
- **Pid**: the launch guards and the pid discovery are the Windows adapter's, unchanged. The command writes `claude.exe`'s pid to `<runs>/<stamp>-<slug>.pid`; after discovery the mod reads it as one more fact: the `worker.found` trace line says whether it matches the probe's pid (`same`, `differs`, `unread`), and the answer names it when it differs. The registry takes the probe's pid either way.
- **Exit**: the command waits for `claude.exe` and exits with its exit code, so the tool's background exit notification carries it.

Verified on the Windows host (Windows PowerShell 5.1.22621, PowerShell 7.6.6), from WSL, with `mod/tests/windows-selftest.py`. It renders the command with the real `powershellLaunchCommand` and runs it as a script under both versions, with `node.exe` and a stub script standing in for `claude.exe`. Three layouts ran under each version: a fresh launch inheriting the config directory, with blanks and a quote in its paths; a picked config directory with brackets, a backtick and non-ASCII letters in the launch directory; and a resume. In each run:
- the argv arrived intact, the name and the settings JSON as single arguments;
- the prompt arrived byte for byte, including non-ASCII text, quotes and CRLF and LF line ends;
- the result file was UTF-8 with no BOM;
- the pid file held the child's pid;
- the exit code came back (0, 3 and 1);
- the working directory was right;
- `CLAUDE_CONFIG_DIR` was inherited or set as asked.

A prompt file under a bracketed folder failed at Start-Process under both versions, as the refusal says. The mocked tests cover the command text (with and without a picker, a resume, blanks and quotes in paths, a title with quotes), the option on Windows and on Linux, and the refusals.

Not verified: no Windows claude session was started through this route by this change (the live proof is the user's to sign off). An earlier scratch variant of this command (the same Start-Process shape, without `-n` and `--settings`) did run one live haiku worker through the PowerShell tool, a fresh launch with a plain ASCII layout. Still unproven live:
- a resume, whose prompt also arrives on standard input;
- non-ASCII or bracketed launch directories;
- the way the tool itself hands the command to PowerShell (the dry runs ran it as a `-File` script);
- whether stopping the background task, or its time limit, also ends the `claude.exe` that Start-Process started.
