# session-control

An orchestrator kit for Claude Code. One interactive session, the orchestrator, launches and manages headless `claude -p` worker sessions and reports their results.

- `CLAUDE.md` holds the orchestrator's instructions. The session reads it from its working directory.
- `mod/` is the session-control mod. It provides:
  - a side panel with the worker sessions, the queued work and the open points;
  - the worker tools `launch_worker`, `acknowledge_workers`, `retire_workers`, `close_worker` and `stop_worker`;
  - the bookkeeping tools `open_point`, `queue_task`, `record_decision` and `archive_decisions`;
  - the read-only inspection tools `list_sessions`, `read_result`, `worker_tail`, `session_writes`, `panel_snapshot`, `audit_state` and `turn_digest`;
  - the licence tools `list_licences` and `probe_licence_usage`, and `launch_worker`'s `config_dir` (see Licence tools): which licences the machine has, by the presence of their files only, and their five-hour and seven-day usage as the CLI shows it, with no credential ever read;
  - a report check that sends a faulty orchestrator report back once;
  - a prompt lint of `launch_worker` (a likely secret or an oversized prompt refused, a missing branch or decision section warned) and a secret scan of what workers return (see Secret scan);
  - notices that tell the orchestrator, one line each, what the poll finds worth acting on: an unregistered session, a stalled worker, a queued task whose blocker finished, an empty queue, a compliance check due, an old open point, housekeeping due, the orchestrator directory's git state, a lock whose holder is dead, a registry that cannot be read, a loaded mod that differs from its source and likely secrets in a worker's result (see Notices and Secret scan);
  - a sign-off guard that refuses a worker prompt instructing a force-push, a remote branch or tag deletion, a mirror or pruning push, a hard reset, a forced clean or `branch -D`, and the orchestrator's own command doing one (see Sign-off guard).
- `model-complexity-matrix.md` is the lookup table for the model and effort of each worker. `CLAUDE.md` requires it at every launch.

## Requirements

- Linux or WSL with `/proc`.
- POSIX `sh` and the GNU tools the mod's shell scripts call: `jq`, `getconf`, `readlink`, `stat`, `sed`, `tr`, `cut`, `ls`, `head`, `tail`, `cat`, `sleep`, `mv`, `rm`, `mkdir`, `test`, and for the listing of `session_writes` without the Node helper `find` (with `-newermt` and `-printf`), `sort` and `awk`; for `stop_worker` without the Node helper `awk`, `kill` and GNU `date` (`+%s%3N`); for the rotation of the debug trace without the Node helper `wc`. They read process facts, list and tail files, and move or remove the files the mod writes. On native Windows `stop_worker` runs the stock `taskkill.exe`.
- `git`, to clone the repository and, for workers, to create worktrees. `audit_state` reads the orchestrator directory's git state with it and says nothing about git where it is missing.
- A Claude Code build that supports mods. Verified on 2.1.296 (Linux, WSL 2).
- Python 3 (standard library only), only to run the self-tests `mod/tests/probe-selftest.py` and `mod/tests/windows-selftest.py`; their Node ports (see Development) need no Python. The mod itself runs no Python.
- Optional: Node.js 22 or newer, as `node` on the PATH or named by the `nodePath` option. With it the mod runs its file operations, its usage probe, the hashing of the drift band and, on Linux, its process probe and the stop of `stop_worker` through its own helper (`mod/helper/`, see Node helper); without it, or with the `helper` option set to `off`, the built-in `sh` (Linux) and PowerShell (Windows) operations run, with nothing to configure. The mod's hooks themselves run inside Claude Code's plugin sandbox, which has no Node.js API. Node.js 22 or newer is also what runs the helper's own tests, the Node self-tests and the Node ports of the end-to-end scripts.
- Optional: a licence picker command, set with the `licencePickCommand` option. `launch_worker` runs it for a fresh launch with `{need}` replaced by the headroom percent (a leading `~/` is expanded); it must print one absolute config directory on stdout and exit 0, or exit 3 when no licence has room. The command is split on blanks (no quoting; a path with spaces is not supported). Without the option a fresh worker gets no `CLAUDE_CONFIG_DIR` of its own and inherits the machine's default configuration: the orchestrator's `CLAUDE_CONFIG_DIR` when that is set, else `~/.claude` with the global config in `~/.claude.json`; the registry records that directory. `CLAUDE.md` leaves licence handling (headroom, reset times, event log) to the user-level instructions in `~/.claude/CLAUDE.md`. On a machine without licence tooling nothing needs configuring: every worker runs under the default config directory, `launch_worker` never refuses for licence room, and the licence steps in `CLAUDE.md` do not apply. A launch given an explicit `config_dir` (a discovered licence, see Licence tools) runs under it and the picker is not run. `list_licences` and `probe_licence_usage` work on any machine, with or without licence tooling.

## Setup

1. Clone the repository. `CLAUDE.md` names the clone's parent directory as the workspaces directory: workers are launched in project directories below it.

   ```sh
   git clone git@github.com:llakeethur/session-control.git
   cd session-control
   ```

2. Start Claude Code from the clone's root with the mod loaded from its folder:

   ```sh
   claude --plugin-dir ./mod
   ```

   `CLAUDE.md` is picked up automatically from the working directory. The mod becomes active only in a directory whose `CLAUDE.md` starts with `# Role: Session Orchestrator`, unless the `orchestratorDir` option is set. Elsewhere `/session-control` answers that the directory is not an orchestrator directory and nothing else happens.

   This repository is not installed through the plugin marketplace. The mod is always loaded with `--plugin-dir`.

## First start

When the mod becomes active it creates each missing helper file from scratch and never overwrites an existing one:

| Path | Created as |
| --- | --- |
| `open-points.json` in the clone | an object with a short `_cleanup` text field and an empty `points` array |
| `task-queue.json` in the clone | an object with an empty `tasks` array |
| `agreed-decisions.md` in the clone | the heading `# Agreed decisions` |
| `open-points-archive.md` in the clone | the heading `# Open points archive` |
| `backups/` in the clone | an empty directory |
| `~/.claude/headless-sessions.json` | `[]` |
| `~/.claude/session-control/runs` | an empty directory |

The bookkeeping tools write a backup of the file they change into `backups/`, once per file, tool and day, before the first change of that day. `~/.claude/session-control/runs` receives each worker's result and error file and the log of retired registry entries (`cleared.jsonl`); a retire deletes the result, error, pid and mod-written prompt files of each session it removes whose outcome was `clean` or whose retire was `reviewed`, only regular files directly in that directory that no other registry entry names (see `retire_workers`). On native Windows `backups/` is created with the first backup, and the runs directory holds the mod's own PowerShell scripts.

## Using it

`/session-control` shows or hides the side panel. Seated inline, the panel shows one section at a time behind a tab strip (`Sessions`, `Queued`, `Open points`, each with its count), and an open log takes the section's place. Docked, the panel has three sections: Sessions, Queued work and Open points. The `[+]` icon in a section's header expands that section to the panel and keeps the other two as one-line headers with their own `[+]`, which expands that section directly (one section is expanded at a time); `[-]` returns to the three boxes, and opening a session's log returns to the log layout (sessions one third, log two thirds); an open log closes by itself, back to the three sections, when its session is no longer in the registry (a registry that cannot be read or parsed, or whose text is empty, keeps the log open). Tracking of runs, the completion handling and the report check run whether the panel is shown or not. The Sessions section lists every registry entry and, as an `orphan` row `(no entry) <cwd>`, each live headless `claude -p` process no entry claims; licence probes are left out: a `claude -p /usage` or token-wake (`claude -p ok`) probe process, whose prompt argument `/usage` or `ok` is followed only by options, is not an orphan, while a worker whose prompt merely contains those words still is. The mod's own probe of `probe_licence_usage`, `claude -p /usage --no-session-persistence`, is left out by the same rule. The elapsed column reads `42s` under a minute, `5m12s` under an hour and `1h05m` from an hour up: a running worker counts from its entry's `started_at`, a finished one shows its run (`ended_at` less `started_at`), and an orphan or a running entry without `started_at` shows the process age the probe read plus the time since that probe; a finished entry without `started_at` or `ended_at` shows `-`. While the panel is shown a one-second display tick recomputes that text and redraws, with no process started and no file read; it stops when the panel is hidden or closed, and the process probe keeps its own `pollSeconds` interval.

Worker completion: when a registered worker's process is gone, the mod classifies its result file and its error file (`clean`, `limit`, `login`, `killed`, `error` or `chatter`). `limit`, `login` and a memory kill come only from reliable signals: the API error status (429, 401), the result text and `errors` of a failed run (`is_error` true or a subtype other than `success`), a result file that is not JSON, and the error file; a result that is a success (`subtype` `success`, `is_error` false, no 429 or 401) is `clean` whatever the error file says (`chatter` when its text is empty, or under 40 characters after a run of a minute, five turns or half a dollar; `killed` when the task notification says its background task was killed), so a benign stderr line such as "usage limit reached, retrying" changes nothing, and the error file counts only when the result is not a success. The cost of that rule: a result file carrying `success` that is followed by a crash or an out-of-memory kill afterwards still reads as `clean`, because the successful result wins over the error file. A failed run's message may sit in `errors` (an array of strings) or in a string `error` field instead of `result`; both are read together for `limit`, `login` and a memory kill. The words of a normal report never count, since a report may quote those messages. The mod then shows a toast led by the notification type (`Session finished`, `Usage limit reached`, `Login needed`, `Session killed`, `Session failed`, `Session ended without a report`; the mod's other toasts lead with `Tracking problem`, `Write not atomic`, `Debug trace failed`, `Node helper`, `More notices` or the title of a notice, see Notices), then ` · ` and the message (a toast is one line of text: the engine draws no line break in it) and, with `completionWrites` on, merges the outcome into the worker's registry entry (it drops `pid`, sets `reported` to `false` and records the harvest time as `ended_at`, epoch seconds). The outcome reaches the model with the next task notification, as the note `session-control completions: <title>: <summary>` (several completions share one note, joined by `; `); the note's free text and the toast's (the entry's title, the outcome's summary drawn from the result file) go through the same redaction as the inspection tools and the notices first, while the session id's first 8 characters, shown for an entry without a title, stay readable; the outcome stored in the registry entry is not redacted. For a `clean` outcome the mod also checks the final report: it must carry the output of `git status -sb` (its branch line) and of `git log --oneline @{u}..HEAD`, each with its exit code, as the worker prompts demand; the log's exit code must sit on its command line, in its output block or right after it, and commits are counted only in that block (it ends at a blank line, a code-fence end, an exit marker, the next `git` line or a heading). When one is missing, when that log exited non-zero or when it lists commits (unpushed work), the completion note gets one more item, `<title>: report check: ...`; the check is tolerant of case, code fences, `$ ` prompts and `exit 0`, `exit=0`, `exit code: 0`, `exit status 0`, `exited 0`, `(exit 0)`, `→ 0`, `-> 0`, `=> 0` or `rc=0`, the number also in backticks (`exit code: \`0\``), and it is a note only: it never blocks anything and never changes the outcome or the toast. It also takes these layouts of real reports: the exit line within 2 non-blank lines after the output block (after its closing fence or after a blank line, in or out of a fence: `## main...origin/main`, then `exit=0` or `(exit 0)` on the next line); an opening fence right below the command (`git log --oneline @{u}..HEAD`, then a fence holding its output, then the exit line); a number alone on its line inside the block as the exit code (`0` below the output); the branch line in backticks inside a sentence (`` `git status -sb` (exit 0): `## develop...origin/develop` ``); both commands named on one line above one block (the block's branch line with its exit code, then the log's line with its own); and a Markdown table whose header has an Exit, rc or code column (the branch line in backticks). Still flagged: a status without an exit code, a log without one, a log of another range (`git log --oneline origin/develop -4`), an exit line further below, and a number inside a sentence (`printed 0 lines`). After a context compaction the next prompt carries a digest of the running workers, the finished workers not yet reported, the open points and the peers that have not acknowledged their task.

### Tools

The tools are registered when the mod becomes active and are named `mcp__session-control__<tool>` to the model.

| Tool | What it does |
| --- | --- |
| `launch_worker` | Starts or resumes a headless `claude -p` worker as a background task, picks the licence for a fresh launch with the configured licence picker command (or uses the default config directory), finds its pid and session id and registers it in the worker registry. A fresh launch takes `dir`, `model`, `effort`, `title` and exactly one of `prompt_file` and `prompt`; optional are `need`, `timeout_minutes`, `resume_sid`, `section`, `rules` and `config_dir` (see Launch parameters). |
| `acknowledge_workers` | Marks finished workers as acknowledged (`reported` true); `keep: true` also marks them as needed for a resume. |
| `retire_workers` | Removes finished workers (no live pid, exit classified) that are not marked keep, whose outcome is `clean` or absent and that no queued or running task names, from the registry, and appends the removed entries to `cleared.jsonl`. The optional `reviewed` input maps a session id (full, or a prefix of at least 8 characters) to a non-empty reason the orchestrator wrote after reading the transcript and finding the stored outcome (`login`, `limit`, `killed`, `error`, `chatter`) wrong, or the work deliberately abandoned: for that session only the outcome check is skipped, and the entry's log line gets `reviewed_outcome` (the stored kind) and `reviewed_reason`; the answer says `Retired with review: <id> (was <kind>: <reason>)` and the debug trace's guard line carries both. A removed session whose outcome is `clean`, or whose retire was `reviewed`, loses its run files: its result file, its error file, the pid file beside the result file (`<result less .json>.pid`, the PowerShell route's) and the prompt file the mod wrote for it (the entry's `prompt_file`), each only when it is a regular file that sits directly in the runs directory: the path under the runs directory is one file name, with no `.` or `..` segment and no further folder (on Windows also no name with a colon, or ending in a dot or a blank), the file is no symbolic link (the path is looked at without following a link; on Windows no reparse point or junction either) and no directory or other non-file, it is no transcript (`.jsonl`) and no other registry entry names it in any field. A path plainly outside the runs directory, a transcript and a file another entry names are left alone without a word. A path with a `.` or `..` segment, one in a subfolder (so also one through a symbolic link to a folder inside the runs directory), a symbolic link and a non-file stay where they are and the answer names each: `(not deleted: <name>: <reason>; ...)` with the reasons `the path has . or .. segments`, `not directly in the runs folder`, `not a plain file name`, `is a symbolic link` and `is not a regular file`. The check of the file itself and the delete are one host operation, `removeRegularFile`: the Node helper's `removeFile` with `regularOnly` (a link or a non-file is refused with the fixed codes `IS_LINK` and `NOT_FILE`), and, when the helper is not there or a call fails, `REMOVE_REGULAR_SCRIPT` under `sh` on Linux and the `removeregular` operation of the file script on Windows, which make the same checks. The answer lists what went (`Run files deleted from <runs>: <id> (<file names>)`) and any file that would not go; the cleared-log line keeps the run's `cost_usd` and `duration_ms`, read from the result file before it is deleted (added to every removed entry's line whose result file holds them). The cleanup refuses nothing: a session the guards let go is removed whatever happens to its files. A resumed session's earlier runs left their own files, which the entry no longer names; `audit_state` lists them as run files no entry names. |
| `stop_worker` | `{session_id, reason?}` (the full id or a prefix of at least 8 characters; `reason` at most 500 characters). Stops a registered worker that is alive and proves it dead: `CLAUDE.md` step 6 (Abort) by tool. Only a registry entry with a recorded pid is reached, never an orphan or an unregistered pid; it is refused (nothing signalled) when the entry has no pid (`refused: session <id> is not alive: its entry records no pid`), when the Abort check before fails (the sessions file `<config_dir>/sessions/<pid>.json` must name the session and its `procStart` must equal field 22 of `/proc/<pid>/stat`; on Windows its `startedAt` must fall in the probe's window around the process creation time: a dead or reused pid is never signalled), and when the pid is this session's own process or one of its ancestors. Then the host's `stopProcessTree` lists the worker's descendants before the first signal and stops the worker: Linux `SIGTERM`, a re-check every second for up to 10 seconds, `SIGKILL` to one still there, re-checks for up to 3 seconds; Windows `taskkill /PID <pid> /T`, the same re-checks, `taskkill /PID <pid> /T /F`; then each descendant still alive the same way. A process is signalled only while it keeps the start its listing found, and a zombie (it has ended; its `/proc` entry stays until its parent reaps it) is never signalled and is reported as exited. The waits run inside the stop's own processes (the helper or `STOP_SCRIPT` on Linux, one short `TREE_PS1` check per second on Windows), never on the engine's clock, so the hook's 10 s budget is not spent on them. Then the Abort check runs again, and it decides the result whatever the stop answered, also when the stop failed or the helper was cut off (its fallback is said in a `Note:` line). The answer is the proof: the pid and session, the reason, the Abort check before, the descendants listed, each signal with its time and exit code and each re-check, the descendants at the end, the Abort check after, the result (`dead`, `exited` as a zombie, or `STILL ALIVE ...: it is a live worker; report it as running, never as stopped`) and every surviving descendant (`still alive`). No registry field is written: the exit notification and the probe record the outcome as for any death. The trace keeps the session id, the pid and the counts (signals, survivors, whether it is dead after), never the reason or the title. |
| `close_worker` | `{session_ids, keep?, reviewed?}`. Acknowledges and retires in one call: exactly `acknowledge_workers` (with `keep`) followed by `retire_workers` (with `reviewed`), through their own code, with their refusals and their answers one after the other (`Acknowledged: ... Retired: ...`), and the run-file cleanup of the retire. `keep: true` only acknowledges and keeps; nothing is retired (a `reviewed` given then is said to be unused). Because the acknowledgement clears a `keep` mark, a kept session closed with `keep: false` is retired, as the two calls in a row would do. |
| `open_point` | Adds, answers, closes, holds or releases an entry of `open-points.json`. Settled entries older than 7 days move to `open-points-archive.md`. |
| `queue_task` | Adds, updates or removes a task of `task-queue.json`. |
| `record_decision` | Appends one numbered line to a section of `agreed-decisions.md`; the section is created when missing. An id that a line of `agreed-decisions.md` already starts with is refused, and so is one that a line of `agreed-decisions-archive.md` starts with, when that file exists (`decision <id> already exists in agreed-decisions-archive.md (an archived section's ids stay taken); choose another id`); an archive that is there but cannot be read refuses the write, since the id cannot be checked. |
| `archive_decisions` | `{sections}`: section headings of `agreed-decisions.md` without `## `, exactly as the file has them. Moves those whole sections (heading line to the next heading, the bytes as they are) into `agreed-decisions-archive.md`, created with the line `# Agreed decisions archive` when missing and only ever appended to, under one dated header line per call (`# Archived <date> from agreed-decisions.md`); the main file keeps one summary line per archived section, `- <heading> (ids <first> to <last>): archived <date> to agreed-decisions-archive.md`, under a `## Archived sections` heading it makes after the file's intro (`audit_state` never counts that section as stale). All or nothing: it refuses a `Standing` section (any heading that starts with Standing), `Archived sections` itself, an unknown or doubled heading, a heading named twice, and a section that a queue task not `done`, a running session (its title or name, or the section it was launched with) or a point with status `open` still names, by its whole heading anywhere in the text (case aside), or, each as a whole word, by a decision id that holds a letter or a branch, T-number or number of five digits or more of its heading; the refusal names each task, session or point. The file is backed up into `backups/` once per day before the first change; the archive is written before the main file, each through a temporary file and a rename against the text read (Linux and Windows). |
| `list_sessions` | Read-only. `{include_finished?}` (default true). A count line, then one line per row of the panel's row builder: each registry entry with its title, session id, name, cwd, config dir, model, effort, status as the panel shows it, pid, elapsed text, outcome kind and summary, cost and keep mark; and each orphan (a live headless `claude -p` no entry claims; a licence run, `claude -p /usage` or `claude -p ok` followed only by options, left out) with its pid, cwd, config dir and age. `include_finished: false` leaves the finished rows out and says how many. |
| `read_result` | Read-only. `{session_id, max_chars?}` (default 12000, 500 to 50000). When the report holds likely secrets the answer ends with the secret scan's line (see Secret scan). The worker's final report: the result file's `.result`; when that is chatter (the `chatter` label of the completion) or there is no result to read (no file, not JSON, no `.result`), the last assistant message of 200 characters or more of its transcript, a message's rows joined and a subagent's rows left out (a real report can sit under late notification chatter). It says the source used and why, the outcome label (and the registry's when it differs), cost, duration, turns, `is_error` and `subtype`, how many replacements the redaction made, and whether the report was cut (the head kept, the characters cut counted). Never the whole transcript. |
| `worker_tail` | Read-only. `{session_id, lines?}` (default 40, at most 200). When the lines shown hold likely secrets the answer ends with the secret scan's line (see Secret scan). The transcript's last lines summarised as the panel's log shows them, the seconds since the transcript was last written (the probe's, else the file's mtime) and whether the process is alive by the Abort check. |
| `session_writes` | Read-only. `{session_id}`. The files written under the session's cwd since its transcript's first timestamp (fractional seconds dropped; the entry's `started_at` when that timestamp cannot be read: no timestamp, the transcript unreadable, or over the read cap, which leaves out a resumed session's earlier runs; with neither, the call is refused), by mtime, newest first, at most 200 with the true count, `.git` and symbolic links left out (host `filesNewerThan`). Each path under the orchestrator directory is flagged `ORCHESTRATOR DIR`, the registry `REGISTRY`; then the transcript's own Write, Edit, MultiEdit and NotebookEdit calls on either, and the commands that name either. By mtime, a write of any other process in that tree shows too. |
| `panel_snapshot` | Read-only. `{}`. The text the panel shows as of its last poll, at 120 columns: the sessions rows (with the warning row when there is one), the open log when one is selected (its last 40 lines), the queued work and the open points (the selected one with its detail), from the panel's own state and row builders, as plain text. |
| `audit_state` | Read-only. `{}`. The end-of-unit audit of the helper files: a facts line (what the registry, queue, open points, `backups/`, the runs directory, `reports/`, `agreed-decisions.md` and git hold), then findings, each with its kind, subject, evidence and a suggested action, high first, at most 40 (the rest counted). High: a helper file that does not parse; a queue status other than exactly `queued`, `running` or `done`; a running task naming no live session (by session id, its first 8 characters or its session name); a queued task whose `waits_for` names a session that is not alive, or holds a full session id no registry entry has (said as retired when `cleared.jsonl` lists it). Medium: finished sessions not acknowledged or not harvested; done tasks still queued; a queued task whose `waits_for` audit_state cannot check (kind `queued-free-wait`): the text is not blank (a `waits_for` of whitespace only counts as no wait and gives no finding), names no registry session (by session id, its first 8 characters or its session name), holds no full session id, and is no licence headroom wait still open. A `waits_for` is a licence headroom wait when its text holds a number followed by a percent sign (`40%`, `40 %`) or the word `headroom` in any case. Every ISO date-time in its text counts as a reset, whether or not the text calls it one: a date `YYYY-MM-DD`, then `T` or a space, then `HH:MM`, with seconds, a fraction and a zone (`Z`, `+HH:MM`, `-HH:MM`, `+HHMM` or `-HHMM`) optional, the letters in either case, that the runtime's `Date.parse` accepts; a date-time without a zone is read as local time; dates written in other forms (`Oct 12 9pm`, a date alone, an hour of one digit) count as no reset. A licence headroom wait is never flagged while its text names no reset or while the latest reset in it is still ahead, and is flagged once that latest reset has passed. The evidence is the `waits_for` text, redacted and cut to 120 characters, and the check is skipped when the registry cannot be read; audit_state lists every such task at each call (the `retire-due` notice tells each once, see Notices); sessions that can be retired (clean, acknowledged, not kept, named by no task that is not done); kept sessions idle for more than 6 hours; open points raised more than 7 days ago; tracked changes uncommitted in the orchestrator directory and how old; a branch other than the default with no worker alive (or a detached HEAD). Low: held open points; backups older than 2 days besides the newest of their kind (the kind is the name without its date); run files no registry entry names (the trace, `cleared.jsonl` and the mod's scripts aside); saved reports; decision sections whose unit no task, entry or open point names (by the branch, T-number or long number of the heading, else two of its words; `Standing` sections never). git runs as `git --no-optional-locks -C <dir>` with read commands only (`rev-parse`, `symbolic-ref`, `show-ref`, `status`), and when git cannot start or the directory is no repository the facts line says `git not checked (no git, or not a repository)` and there is no git finding. |
| `turn_digest` | `{}`. Writes no file (the time of the call goes to the mod's store, `$.store`, under `digest:<orchestrator directory>`, a key dropped, as the notice state's is, at the first notice pass of a load once that directory is gone). What changed since the previous call: the worker completions the mod harvested, then the notices it delivered, by section (sessions that became orphans, sessions that stalled, queue tasks that became ready, open points that aged past 24 hours), each with its one line; the notices of every kind by count (`notices fired: queue-ready 1, open-point-age 1, retire-due 1`); the unacknowledged peer messages; one state line (`state: 2 alive, 3 finished; queue 1 queued, 0 running; 4 open points`, from a fresh read of the registry with the probe, the queue and the points; `registry unreadable` when it cannot be used); `nothing new` when the ledger is empty and no peer message is unacknowledged. Then everything is marked seen. The first call reports from the mod's load (`since the mod's load at <UTC time> (...; first call)`). At most 40 lines: the longest section is cut first and says `- ... N more`. Each line goes through the redaction of the other tools; when a completion it reports held likely secrets, the answer ends with the secret scan's line (see Secret scan). The ledger lives in memory for the load (at most 500 events, the older ones counted): a reload of the mod starts a new one, and a call after a reload says `the mod was loaded again at <time> and keeps what happened from then on only`. With the `notices` option off it reports the completions and says the notices are off. The peer part reads the ledger the report check uses: a message the model sent to a peer (`session.send`) stays open until a peer reply arrives that names the peer (or, with exactly one open, any peer reply); the ledger is the session's own, lost on a reload, so it can miss an acknowledgement or keep one that came as a reply naming no peer. A delivered reply carries no sender name, so the ledger can only read the reply's text (`ackPeerNote` in `hooks/core.ts`): a reply from B that names A acknowledges A, while B stays open; a reply that names no peer while two or more are open acknowledges none of them; with exactly one open, any peer reply acknowledges it, whoever sent it. |
| `list_licences` | Read-only. `{}`. The licences of the machine (see Licence tools): one line per licence with its `config_dir`, `name` (`default`, else the last path component), `source` (`default`, `home`, `child`, `dash`, `explicit`), `logged_in` (both files present as regular files: presence and kind only) and the registry sessions under it (live by the Abort check, and in all, matched by `config_dir` normalised but not symlink-resolved), after a summary line that says whether the directory scan was fresh or how old the kept one is. At most 50 licences (the rest counted); registry entries under no discovered licence are counted; a registry that cannot be read gives `?` counts and the reason. |
| `probe_licence_usage` | Read-only. `{config_dir?}`: one discovered licence by its `config_dir` or its name; any other value is refused with the fixed text `not a discovered licence`; absent, every discovered licence. A summary line (how many were probed now and how many answered from the cache, the highest five-hour and seven-day figures with their licence), then per licence `five_hour <percent>% (resets <text>)` and `seven_day <percent>% (resets <text>)` (`-` for a window the CLI did not show) or `error <code>`, with `age_seconds` and `cached`; the licences a call left out are named (`N more not probed: call again (...)`), and a last line says how far the figures can be trusted (see Licence tools). |

`launch_worker` refuses, among other cases: a launch directory that is the orchestrator directory or `$HOME`; both or neither of `prompt` and `prompt_file`, or a blank `prompt`; a `section` the decisions file lacks; a missing or empty prompt file; a prompt that lacks a foreground wait, the `git status -sb` report line or the no-attribution instruction (a prompt that says "skill test" is exempt); a prompt that holds a likely secret (the secret scan's kinds, see Secret scan: `refused: the prompt holds a likely secret (aws-key on line 3); a prompt never carries a credential: name where the worker finds it (an environment variable, a credential helper), never the value`, up to five finds by kind and line, never a value; a skill test is not exempt); a prompt of more than 60000 characters (`PROMPT_MAX_CHARS` in `hooks/lint.ts`: `refused: the prompt has N characters, the limit is 60000: reference a long document by its file path for the worker to read instead of pasting it into the prompt`; a skill test is exempt); a resume of a live session; a licence pick that exits 3 or prints nothing usable. A worker is started as `claude -p --model <model> [--resume <session id>] -n <name> --settings '{"crossSessionInbound":"accept"}' --dangerously-skip-permissions --output-format json -- <prompt>` with `CLAUDE_CONFIG_DIR` set to the worker's configuration directory (left out when that is the default directory, which the worker then inherits) and `CLAUDE_CODE_EFFORT_LEVEL` set to the requested effort, through the Bash tool; on native Windows with the `launchRoute` option at `powershell`, through the PowerShell tool instead (see PowerShell launch route).

The secret scan, the size cap and the sign-off guard run on the prompt as it is launched (the text given or read, with the section's block and the rules block appended), before the licence picker runs; the check of the three items and of a missing or empty prompt file runs after the pick. A refused prompt starts nothing and writes no prompt file. Three checks only warn: the sign-off guard's push to `main` or `develop` (see Sign-off guard), the licence usage warning of `config_dir`, and this one: a prompt that asks to commit, push or work on a branch (the words commit, push or branch in a sentence with no negation such as no, not, never, without, stop before; the rules block's own words do not count) but names no branch (the word branch with a name in backticks or quotes, a gitflow name such as `feature/x`, or main, master, develop after it in the same sentence; a gitflow name anywhere; or "create one") and no decision section (the block a `section` appends, `agreed-decisions`, a "decision section", or `section "<heading>"`) is launched, and the answer ends with the line `WARNING: the prompt asks to commit, push or work on a branch but names no branch (an existing one by exact name, or "create one" with its gitflow prefix) and no decision section; the worker may pick one itself`. A skill test gets no warning.

Launch parameters:

- `prompt`: the prompt as text instead of `prompt_file` (exactly one of the two, else a refusal). The mod writes it to a prompt file of its own beside the run's result file, `<runs>/<session name>.prompt.md`, outside any repo, named by the launch's unique session name (`w-<slug>-<yyMMddHHmmss>`, with its `-2` suffix when that is taken), so two launches of one title in one second write two files (a resume keeps its entry's name, so its file adds the resume's time: `<runs>/<session name>-<yyMMddHHmmss>.prompt.md`), and launches with that path; the file is written only once the guards have passed, so a refused launch leaves nothing.
- `section`: a section heading of `agreed-decisions.md` (without `## `). Its lines, as the file holds them, are appended to the prompt after a blank line under `## Binding decisions (section <heading>)`; a heading the file lacks (or has twice), a decisions file that cannot be read, or a `prompt_file` that cannot be read is a refusal. With a `prompt_file`, the mod writes the extended copy as its own prompt file and leaves the given file as it is.
- `rules`: whether the standard rules block (`RULES_BLOCK` in `hooks/core.ts`) is appended when the prompt lacks one of the items the launch guard checks (a foreground wait, `git status -sb`, the no-attribution instruction). The block carries the worker-prompt items of `CLAUDE.md`: no AI attribution trailer and no agent mentioned in anything written; no human answers during the run, look up, then a documented default, never for a sign-off item; never read, print or pass a credential; long runs with `run_in_background: true`, an explicit timeout, foreground waits under ten minutes in `until` loops, never ending the turn while a run is live; the report with `git status -sb` and `git log --oneline @{u}..HEAD`, each followed by its exit code. A prompt that already carries the guard's items, or a skill test, gets no block, so it never gets a second copy. Default: true when the mod writes the prompt (`prompt` given, or a `section`), false for a `prompt_file` given alone, which is launched as it is and refused when it lacks the items.
- A resume (`resume_sid`) may leave out `dir`, `model`, `effort` and `title`: they are taken from the registry entry (its `cwd`, `model`, `effort`, `title`); a value given wins, and the answer adds `From the entry: <fields>.` (before any `WARNING:` line). The resume runs under the entry's config directory.
- `config_dir`: a discovered licence (see Licence tools), by its `config_dir` or its name. It wins over the licence picker for a fresh launch: the picker is not run, the directory is the worker's `CLAUDE_CONFIG_DIR` (left out when it is the default directory, as a launch without a picker runs there) and the registry records it in `config_dir` as for any launch; the answer adds `Licence: <name> (config_dir given; the licence picker was not run).`. A value that is no discovered licence is refused before anything runs, naming only the discovered licences: `refused: config_dir is not a discovered licence (discovered: default, second; list_licences shows them); nothing was launched`. There is no refusal for licence room (the caller chose the licence), but when a `probe_licence_usage` probe of that licence made in the last 60 s showed either window over 90 percent, the answer ends with `WARNING: licence <name> was over 90% in a probe <n> s ago (five_hour <p>%, seven_day <p>%); launched as asked, it may stop at its limit`, naming each window over 90 percent. The launch never probes: only a probe already kept warns. A resume runs under its entry's own `config_dir`: given with `resume_sid`, the entry's own directory is accepted and any other is refused (`refused: a resume runs under its entry's own config_dir (<dir>), not <dir>; nothing was launched`).

When the mod wrote the prompt file (`prompt` given, or a section or the rules block appended), the answer says `Prompt: <path> (written by the mod[; ...])`, naming what was appended, and the entry records `prompt_file` (the mod's prompt file, which a retire deletes) and `section`. The debug trace records `rules` and a `launch.prompt` line (the prompt file's path and length, whether it was inline and what was appended), never the prompt text or the section heading.

Inbox: every worker gets a session name with `-n` and accepts messages from other sessions on the machine (`crossSessionInbound` set to `accept` through `--settings`), so the orchestrator can send a running worker a message by its name. The name is `w-`, the slug of the title cut to 24 characters, and the launch time in UTC as `yyMMddHHmmss` (for example `w-fix-the-parser-261010143117`): letters, digits and dashes, at most 39 characters before a uniqueness suffix; a name already in the registry or given out by the same session gets `-2`, `-3` and so on. The uniqueness check covers only the registry and the session's own names, so two orchestrator sessions starting workers with the same title in the same second can still get the same name. A resume passes the same two flags and keeps the entry's name, so a session answers to one name across resumes; an entry without a name (launched before names existed) gets a fresh one. The worker's exit is still detected through the background task's notification.

Registry entry: `launch_worker` records `title`, `pid`, `session_id`, `name`, `socket_path`, `config_dir`, `cwd`, `model`, `effort`, `result_file`, `err_file` and `started_at`, the time the launch started the run in epoch seconds, and, when the mod wrote the prompt, `prompt_file` and the `section` appended; a resume sets the new run's `started_at` and drops the previous run's `ended_at`. Entries written before these two fields existed stay valid without them. `name` and `socket_path` come from the worker's sessions file `<config_dir>/sessions/<pid>.json` (`name` and `messagingSocketPath`), read with the session id; `name` falls back to the name the launch passed. A claude that writes no socket (an older version) gives an entry without `socket_path`, and a resume then writes `socket_path: null` so the previous run's socket is not kept. The socket is valid only while the pid lives. The launch answer names both.

The six inspection tools change nothing: they write no file and start no process but the process probe, a transcript tail, the listing of `session_writes` and the git reads of `audit_state` (on Windows without Node a PowerShell script is written to the runs directory before its first run, as every PowerShell operation of the mod does). A session id is the full id or a prefix of at least 8 characters; an unknown one, or one two entries share, is a refusal that says so. Each answer is plain text of a bounded size (at most 60000 characters, then a line saying how much was cut; `read_result`'s report is held to `max_chars`). Every free text read from the registry, a result file, a transcript or a helper file goes through the debug trace's redaction (`redact` in `hooks/trace.ts`: keys, tokens, JWT parts, `key=value` and `--flag value` secrets, URL user info, curl's `-u user:pass`, `--user user:pass` and `--user=user:pass`, also with a quoted password that holds blanks (`-u 'alice:s3cret pw'`) (not docker's numeric `-u 1000:1000`, not a value whose second part starts with a slash or, quoted, a blank; known over-redaction: any other value of the form `name:name` after `-u` or `--user` cannot be told from a credential and goes, whatever the command, so `--user www-data:www-data`, `docker run -u root:root`, `sort -u a:b`, `echo -u foo:bar` and `git push -u origin:main` show `[redacted]` too), long runs of letters and digits become `[redacted]`; a UUID and a plain path stay), so a long hex string shows as `[redacted]`. The exception is a git object id: a lower-case hex string of exactly 40 or 64 digits that is no part of a longer run of letters and digits, on a line that is evidently git, is shown as it is, so `origin 7ebdad1d... refs/heads/main` of a `git ls-remote` reads whole. A line is evidently git when it has `refs/`, `commit ` (the word and a blank), `HEAD`, a range of two hex ids (`a..b`, `a...b`), `git ls-remote`, `git log`, `git rev-parse` or `sha` as a word (`sha`, `sha1`, `sha256`), or when the id starts a `git log --oneline` row (the id, a blank, a subject). Each line decides for itself, so an id alone on its line (the output of `git rev-parse HEAD`) is redacted; so is an id right after `key`, `token`, `secret`, `password`, `auth` or `credential` or after `=` or `:` (`sha: <id>` and `sha=<id>` too), an id of any other length (32 to 39, 41 to 63, over 64), one in upper case and one inside a longer run. The debug trace uses the same function. File names are redacted as paths are, so a dated name reads whole. The mod's own identifiers are exempt: a session id of the UUID form is shown as it is wherever a tool names a session (`list_sessions`, the heading of `read_result`, `worker_tail` and `session_writes`, an ambiguous-id refusal), and a session name of exactly the form a launch generates in `list_sessions` and in `stop_worker`'s answer. That form is `w-`, the slug (lower-case letters, digits and dashes, maybe empty), `-`, twelve digits (`yyMMddHHmmss`) and an optional `-<number>` suffix, at most 64 characters (`GENERATED_NAME` in `hooks/core.ts`); a resumed session keeps its entry's name, which has that form. Any other value in those fields is free text and redacted: a name without the twelve-digit stamp, one with an upper-case letter or a blank, one of more than 64 characters, and a secret-shaped lower-case string behind `w-` among them. Terminal control sequences are dropped. No tool reads `.credentials.json` or `~/.claude.json`. The trace records each call's named fields and the answer's length only (`resultChars`), never its text.

`acknowledge_workers` and `retire_workers` refuse a worker whose process is alive. `retire_workers` also refuses a worker that is marked keep, whose outcome is not `clean` (unless `reviewed` gives a reason for it) or that a queued or running task names. A `reviewed` entry never lifts the other refusals (a live, kept, unclassified, queue-named or unknown session), and one without a reason, or naming a session that is not in `session_ids`, is refused.

### Notices

The orchestrator is a model session: it hears of a worker's exit through the harness and of everything else only when it looks. The mod already knows more at each poll, so it tells the orchestrator the useful part, sparingly. Each notice is:

1. one line the model reads, `session-control notice: <kind>: <message>`, kept until the next prompt of any origin (a prompt the user types, a task notification, a peer message) and handed to the model as that prompt's additional context, the lines joined by line breaks, after the `session-control completions: ...` note when there is one (at most 30 lines wait: past that the first 29 stay and the last says `session-control notice: more: N further notices not shown; run list_sessions and audit_state`, its count growing with each notice that does not fit, so nothing is dropped silently); under the hold rule a notification-only turn answers with one line, so a notice is one line too;
2. a toast, `<title> · <message>` (one line), the title by kind as in the table; at most 3 per source in one pass (the poll's notices of a refresh, the notices of all the harvests of that refresh together, a queue change's, an inspection tool's (`read_result`, `worker_tail`) and the drift check's), the rest told by one toast at the end of that pass, `More notices · N more notices: see the next prompt` (a refresh that harvests and polls can thus show up to 6 notice toasts and the one summary);
3. with the debug trace on, a `notice` line with the kind and the notice's ids, counts and switches (a pid, a session id, a task or open point id, how many), never its text, a title, a section heading or a path.

Of the orphans that come due at one poll, the first 5 are told one notice each and the rest in one notice, `orphan: N more unregistered sessions: <the first 10 pids> and M not listed; list_sessions shows each; raise an open point naming them`; every one of them is marked told in the debounce state, so none is told again.

No notice starts a turn: the mod never submits a prompt of its own, so an idle orchestrator reads them with its next prompt, and sees the toast at once. The option `notices` (`on` by default) at `off` turns every one of them off (lock-holder, registry-unreadable, mod-drift and secret-in-result included: no lock folder is read then); the completion notes and their toasts stay, and so does the drift band above the prompt, which is a display and no notice (the `modSource` option at `off` hides it).

Every time rule reads the mod's clock (`$.clock`), which the tests drive with the mocked clock. Beyond the poll's own reads (the probe, the queue, the open points and the registry), the notices run one process probe per lock check (lock-holder, at most once a minute), one hash of the two mod folders per drift check (mod-drift, at most once every 5 minutes) and git for repo-state, at most once per hour; an orphan's sessions file is read once, when its 30 seconds are up; `cleared.jsonl` is read only while retire-due is due. The notices of what every refresh reads (orphan, stall, open-point-age, and the re-arming of unit-complete) also run when the board turns on (the session's start, `/session-control`) and after a tool's own refresh; retire-due and repo-state come only from the poll's timer, from its first tick on.

Their debounce state is kept in the mod's own store (`$.store`, a JSON file of the engine's under the user's configuration directory, kept between sessions and hot reloads) under one key per orchestrator directory, `notices:<directory>`, so a reload of the mod, or a new session in the same directory, tells nothing again; it is pruned at each poll (a pid, session, task or point that is gone leaves it), and the key of an orchestrator directory that no longer exists is dropped at the first notice pass of a load. A store that cannot be read or written keeps the state in memory for the load (one `error` trace line, `notices.store`).

A registry the poll cannot use is never taken for an empty one: when the registry file is missing or cannot be read, is empty or only whitespace, or does not parse as a JSON array (`isRegistrySound` in `hooks/notices.ts`), that poll skips every notice step that reads the registry, their pruning included: orphan (no orphan timer starts, none is forgotten), stall (a stall told stays told), the pruning of the queue-ready and compliance-due state (those two come from a harvest, which needs registry entries), retire-due and repo-state. Their state stays as it was and nothing of theirs fires, so a registry that flaps between readable and not tells a stalled worker once, and a registered live worker never becomes an orphan notice. Open-point-age and the re-arming of unit-complete, which read only the points and the queue, still run, except after a registry that does not parse: that refresh shows the panel's warning and runs only registry-unreadable and, from the poll's timer, lock-holder and the drift check. A registry that reads as `[]` is a sound, empty registry: a live headless claude it does not claim is an orphan.

`/session-control` raises no prompt and drains no notice: the lines wait for the next prompt. The 24-hour, hourly and 15-minute rules are covered by the mocked-clock tests.

### Secret scan

The tools already redact (see the inspection tools above); the secret scan (`hooks/secrets.ts`) also says what it found. It looks for likely secrets by kind:

| Kind | What |
| --- | --- |
| `private-key` | a `-----BEGIN ... PRIVATE KEY-----` block (RSA, EC, OpenSSH, PGP, encrypted), masked from its header to its END line; with no END line before the next BEGIN header (a key cut off in a report), to the first blank line after at least one body line (armor header lines such as `Version:`, `Proc-Type:` or `DEK-Info:` are no body lines), never past the next BEGIN header and never more than 4,000 characters after the header (`PRIVATE_KEY_MAX_BODY`), so a header without its END line cannot hide the rest of a report |
| `github-token` | `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_` with 20 or more letters and digits, `github_pat_` with 20 or more letters, digits and underscores |
| `sk-key` | `sk-` (also `sk-ant-`, `sk-proj-`, `sk-live-`, `sk-test-`) with 16 or more characters, a letter and a digit among them |
| `slack-token` | `xoxb-`, `xoxa-`, `xoxp-` (and `xoxe-`, `xoxr-`, `xoxs-`) with 10 or more characters |
| `aws-key` | `AKIA` or `ASIA` and 16 upper-case letters or digits |
| `bearer-token` | `Bearer` and 20 or more token characters |
| `url-credentials` | `scheme://user:password@` (a URL with a user and no password is none) |
| `secret-assignment` | `NAME=value`, `NAME: value`, `"name": "value"` or `--name value` whose name's last part is password, passwd, passphrase, token, secret, credential(s) or apikey, or key after api, access, private, secret, signing or auth (`DB_PASSWORD`, `nadir_access_token`, `ANTHROPIC_API_KEY`; not `max_tokens`, `tokenState`, `AuthKeywords.robot`), the value on the same line, 6 characters or more with a digit or 12 or more, and no placeholder (`$VAR`, `<...>`, `[...]`, `{...}`, `***`, `xxxx`, `changeme`, `example`, `none`, ...) |
| `keyed-blob` | a hex run of 32 or more, or a base64-like run of 24 or more with a letter and a digit, within 24 characters after key, token, secret, password, passwd, passphrase, credential, auth, bearer or signature |

A UUID, a generated session name and a plain path are never a find; a git id in a git context is no find either (no rule matches it), nor is a `sha256sum` line (its hex run is redacted by the general redaction and not counted as a likely secret). Each value found is replaced by `[redacted]` before the general redaction runs (the name, the scheme or the word `Bearer` stays), in every free text the tools show (`clean` in `hooks/inspect.ts`), so a value the general redaction would keep is gone too. Where a worker's output is read, the answer ends with one line, `secret scan: N likely secrets redacted (kinds: <kinds>)`, the kinds in the order of the table, never a value and never a position: `read_result` (the report it shows; its `redaction:` count includes the scan's replacements), `worker_tail` (the lines it shows), the completion note (as its last item, `<title>: secret scan: ...`, after the outcome and the report check, from the result's report) and `turn_digest` (the sum over the completions it reports, kept within its 40 lines). It also raises the `secret-in-result` notice (see Notices), once per entry; with the `notices` option off the line stays and the notice does not come.

Limits: it is a heuristic. A secret of another shape (a short password in prose, a key without a key word before it) is not counted, though the general redaction may still replace it. Known false positives, accepted: a key word followed by a colon in prose (`couldn't fetch token: AADSTS70011x`, `without credentials: mongo7x`), and a value quoted as an example (a base64 sample after `token:` in a README quote): the scan cannot tell an example by its context, so it counts and masks it.

### Loaded-mod drift band

The orchestrator's live mod is often a copy of the repository's `mod/` folder (the hot-reload folder), and the copy can lag behind the repository unnoticed. In the orchestrator directory the mod compares the loaded plugin's own folder (`$.plugin.root`) with the source mod folder and, while they differ, shows one dim line in the band above the prompt input, where the engine shows its "Update installed" line:

```
session-control: the loaded mod differs from /home/u/session_control/mod (1 file changed: hooks/drift.ts). Reload it: copy hooks, helper, types and plugin.json to the plugin folder, or restart with --plugin-dir /home/u/session_control/mod
```

The count, up to three file names (then `...`) and nothing else. The line is drawn above what the band would show without it (the hook's `next(e)`: another plugin's band beneath, or the engine's own line), which stays drawn below it; while a survey is above the prompt the drift line is not drawn. The first time a set of changed files is seen it also raises one toast titled `Mod out of date` and one `mod-drift` notice line (see Notices). The band goes at the first check that finds the two folders alike.

- **Source**: the `modSource` option; empty, `<orchestrator directory>/mod` when that folder exists; `off`, no band. A source that is not there shows nothing; the same folder (a session started with `--plugin-dir` on the source itself) never differs.
- **What is compared**: the files directly in `hooks/`, `helper/` and `types/`, and `.claude-plugin/plugin.json`, by content, line ends aside (a CRLF counts as an LF, so a copy checked out with other line ends is no drift; a file holding a NUL byte is compared byte for byte); never `tests/`, `node_modules` or the engine's generated `.claude-plugin/types`, and no folder inside those three. No symbolic link inside either folder is followed or hashed: neither a link that is a compared file or folder nor one among the folders on the way to it (a `.claude-plugin` that is a link: its `plugin.json` is passed over, as absent); the plugin's folder itself is taken as the engine names it.
- **How**: one host call hashes both folders with one method. The Node helper's `hashTree` (one `batch` of two steps in one process): SHA-256 over each file's bytes with each CRLF folded to LF (a file with a NUL byte as it is), relative paths and hex digests only, at most 500 files and 8 MiB per file. Without Node, or when the helper call fails, the native operation through `$.fs` (`list`, `stat`, `read`): cyrb53, a 53-bit hash, over each file's bytes read with `$.fs.read(path, { as: "bytes" })` and folded the same way, so two files that differ only in bytes that are no UTF-8 (`0xff` against `0xfe`, which a text read decodes alike) still differ; an engine that answers a byte read with text gets cyrb53 over that text with each CRLF folded, and there such bytes are not told apart. Files up to `$.fs.read`'s 4 MiB. A folder that cannot be read, more than 500 files or a file too large shows nothing, never an error band.
- **When**: at the board's start and then from the poll at most once every 5 minutes (`DRIFT_EVERY_SEC`), in the background of the poll. For a real test run only, the interval can be shortened: `SESSION_CONTROL_DRIFT_SECONDS=<5 to 299>` counts only together with `SESSION_CONTROL_TEST=1` in the session's environment (any other value, or the first alone, leaves 5 minutes), as the helper's `SC_HELPER_TEST` rule does.
- **The notices option**: `notices` `off` keeps the band (it tells the person at the screen, not the model) and drops the toast and the line.

With the debug trace on, each check writes one `drift` line: whether the source is there, whether the folders were compared and how many files differ.

### Lock folders

The lock-holder notice reads the folders the `lockDirs` option names (comma separated absolute folders; empty: off), at most once a minute from the poll, read-only: no lock is ever deleted, written, moved or touched. A lock is a direct child of one of them:

- a folder (not a hidden one) holding a file named `pid`, `owner` or `holder` (the first of them there): its holder is the first whole number in that file's first line;
- a file named `*.pid` or `*.lock`: the same rule over the file itself; or, when the file is JSON (as the NADIR project's `StackLocks.py` writes `/tmp/nadir-locks/<name>.lock`: an indented object with `pid`, `pid_start`, `worker`, `cwd`, `host`, `purpose` and `acquired_at`), its `pid`, and on Linux its `pid_start` (field 22 of `/proc/<pid>/stat` when the lock was taken), which must still be the pid's own start, else the pid was reused and the holder is gone.

A link, any other file (the lock tool's own `.guard`) and a hidden folder are passed over, at most 50 locks per folder are read. A holder that cannot be read, a text with no number in its first line, a number after a minus sign, 0 or one too large, and JSON that is not an object with a `pid` are skipped without a notice. The holders' pids are proved alive by the process probe (one call for every lock of the check). On Linux a holder whose process is a zombie (state `Z` in `/proc/<pid>/stat`, which the probe's `A` line carries as its last column: it has exited and its parent has not reaped it) is dead, as the NADIR project's `StackLocks.py` reclaim treats it, and the notice says `which has exited: it is a zombie its parent has not reaped`; a JSON lock whose `pid_start` is not the live pid's own start is dead too, and its notice says `which is no longer running as that process (its JSON pid; the pid now belongs to a process started at another time)`; a pid that is gone, `which is no longer alive`. On Windows the folders are taken in the `C:/...` form, `pid_start` is not compared and no zombie is told (the Windows probe carries no state).

### Sign-off guard

The orchestrator's rules (`CLAUDE.md`, Scope) list the actions that need the user's go-ahead in the conversation, among them a push to a protected branch where the project's push policy asks, a force-push or any rewrite of pushed history, deleting a remote branch, tag or PR, `reset --hard`, `checkout --`, `clean`, `branch -D` or a forced `worktree remove` over uncommitted work, stopping a shared live stack, and sending anything outside the repo. The mod cannot know whether the user gave that go-ahead, so it acts at the two places it controls, and only for the actions it can read from text:

1. **The worker prompt** (`launch_worker`, `hooks/lint.ts`). A prompt that instructs, as a step the worker should run, a force-push (`push --force`, `push --force-with-lease`, `git push -f`, a `+` refspec, the words force-push or force push), a remote branch or tag deletion (`push --delete`, `git push -d`, `push origin :ref`), a mirror push (`push --mirror`), a pruning push (`push --prune`), `reset --hard`, a forced clean (`git clean -f`, `-fd`, `-fdx`, `--force`) or `branch -D` (also `git branch -d -f` and `--delete --force`) is refused. A short flag cluster (`-f`, `-d`, `-fd`) counts only after `git push`, `git clean` or `git branch` (with git's own options, `git -C /r push -f`, between them), and so does every flag of clean, an English word: the `-f` of `make -f`, `tail -f` or `rm -rf` is no git flag, and `rm -rf` is not on the list. A long flag (`--force`, `--force-with-lease`, `--delete`, `--mirror`, `--prune`, `--hard`), a refspec and branch's `-D` count after the bare verb too. A command's words end at a quote, a backtick, a parenthesis, `|`, `;`, `&`, a punctuation mark before a blank, or a word that starts another clause (then, and, or, after, before, when, if, so, but, until, while, once, unless, except), and after at most 12 words, so `Push the branch, then make -f build.mk` names no flag of the push. A past form describes and is passed over: `force-pushed`, and a bare verb or force-push word right after was, were, been, being or had (`the tree was reset --hard`).

   A sentence that says the worker must not do it is allowed. The negation window is counted from the action's own token (the flag of `push --force`, the `--hard` of `reset --hard`, the refspec, the force-push word), not from the verb: a negation at most 20 words before the token or 6 words after it (`NEGATION_WORDS_BEFORE`, `NEGATION_WORDS_AFTER` in `hooks/lint.ts`), in the same sentence or list item, with no contrast word (but, however, then, instead, yet, otherwise, except, unless) between the two; a negation in the sentence before never covers the next one's action. The negations: not (do not, must not, may NOT), never, nothing, neither, nor, don't, doesn't, mustn't, shan't, shouldn't, won't, cannot, can't, refrain, avoid, forbidden, prohibited, disallowed, stop before. No and without count only when they govern the action, with at most three of the words any, a, an, the, other, more, further, git, ever, use, using, run or running between (`no force-push`, `without force-pushing`, `no \`git push --force\``; not `git push --force with no prompt`). A go-ahead or a sign-off is no negation on its own; it counts as a gate only in the forms "needs (or requires) the user's go-ahead, sign-off, approval, permission or consent" and "is a sign-off item" (`A force-push needs the user's go-ahead: stop and report.`; not `Get the go-ahead, then force-push.`). A refusal word before the action (refuse, refused, deny, denied, denial, reject) or a passive one after it (`... must be refused`) counts too, so a sentence about the guard itself passes. A `--no-...` option is no negation. So `Push main to both remotes, fast-forward only, never --force.` passes (the push names no flag before the comma, and `never` stands right before `--force`), as does the standard `You may NOT merge to main, push to another remote, rewrite history, delete a branch, or force-push.`

   A negated list is negated item by item: the items after a colon or an opening parenthesis whose 8 words before hold a negation, a gate or a refusal word (`never: force-push, reset --hard, branch -D`; `actions that need the user's go-ahead (..., force-push, ...)`), up to a contrast word, and after a parenthesis up to its closing one, and the bullet or numbered items under a head line that ends with a colon and whose last sentence holds a negation or a gate (`You may NOT:`, `Never run these:`), up to a blank line, a line that is no item, or a sibling of a bulleted head; an item with a contrast word before the action is not covered (`- skip the tests, but force-push the branch`).

   A quoted example passes: an action inside backticks or double quotes after an introducing word in its sentence (refuse, refused, deny, denied, reject, example, e.g., for instance, form or forms, such as, attack) with no contrast word between, or a line of a fenced code block whose last non-blank line before it holds such a word or is a negating head. `The guard refuses \`git push --force\` and \`git branch -D x\`.` passes; `Run \`git push --force origin x\` now.` and a fenced block after `Steps:` are steps and are refused.

   A prompt that names a push to `main` or `develop` in a sentence without such a negation is launched with a WARNING line, since whether that push needs a go-ahead depends on the project's push policy. The refusal says that the user's go-ahead is a sign-off item and how to proceed: raise an open point for it; the mod never passes the step to a worker, so with the go-ahead the user runs the step or says how, and a worker prompt may still say to stop before it and report. The phrase "skill test" exempts a prompt from the three-item check, the size cap and the branch warning, never from the secret scan or this guard.
2. **The orchestrator's own commands** (`hooks/guard.ts`, a `tool.call` hook on `Bash` and `PowerShell` in the orchestrator directory's own session: the session started there, with the board on). A Bash or PowerShell command that runs one of those same git actions (`git push` with `--force`, `-f`, `--force-with-lease`, a `+` refspec, `--delete`, `-d`, a `:ref` refspec, `--mirror` or `--prune`; `git reset --hard`; `git clean` with `-f` or `--force`; `git branch -D`, or `-d`/`--delete` with `-f`/`--force`) is refused, read by its text as Bash reads it (a heredoc body that data sinks, an interpreter or `xargs` read is text, as is a quoted argument; `sh -c`, `eval`, `powershell -Command`, substitutions, a heredoc a shell or another command reads and a here-string a shell reads are code; an interpreter's code is not read for git commands; git's own options before the subcommand, `-C <dir>`, `-c <key=value>`, `--git-dir=...`, are passed over). `git fetch --prune` and `git remote prune` are not pushes and run. The orchestrator never pushes or resets: this repository's rules give those actions to workers. A call the mod makes itself (the launch's `Bash`) passes untouched; in any other session (another directory, also with the `orchestratorDir` option set, or a session started elsewhere that turned the board on with `/session-control`) the hook does nothing. With the debug trace on, a refused command is a `guard` trace line with `check: sign-off`, the tool and the git action (`git push --force`), never the command, and a refused launch prompt one with `check: prompt-lint` or `check: sign-off` and the reason.

Built exactly this and no wider: a plain push, a push to a protected branch by the orchestrator, a push to a repo marked local-only, deleting a PR, `checkout --`, a forced `worktree remove`, a stopped stack and anything sent outside the repo are not checked by the mod (the rules still put them on the sign-off list). It is a slip guard, not a security boundary: it reads the words of a prompt and of a command. It cannot see an alias (`git config alias.fp "push -f"`, then `git fp`), a script file, a command built at run time or read from a file, a step described in other words ("overwrite the remote branch"), or a negation further away than its window; a sentence that negates something else near the action (`Do not wait: force-push.`), a negating head line over a list of steps, an introducing word before a quoted command that is meant as a step (`For example, run \`git push --force\` now.`) and a bare `push -f` without `git` pass; and it can still refuse a prompt that quotes such a command as an example without an introducing word or a negation.

### Licence tools

A licence is a config directory, the one a launch selects with `CLAUDE_CONFIG_DIR`. `list_licences` finds them, `probe_licence_usage` reads their usage, and `launch_worker`'s `config_dir` launches under one of them. The three work on any machine, with or without licence tooling; none of them is a trigger or runs by itself.

- **Discovery** (`hooks/licences.ts`): the candidates, in this order and each directory once (paths compared as the platform compares them, the first source wins): `default`, the directory a launch without a picker and without `config_dir` uses (the orchestrator's own `CLAUDE_CONFIG_DIR` when it has one, else `~/.claude`: what the registry records for such a launch); `home`, `~/.claude` when it is not the default; `child`, every directory `~/.claude/<name>/`; `dash`, every directory `~/.claude-<name>`; `explicit`, each entry of the `licenceDirs` option. On Windows `~` is `HOME` when that is a Windows absolute path (Git Bash's `/c/Users/<you>`), else the profile folder (`%USERPROFILE%`), `C:/Users/<you>/.claude` in the stored form. A candidate counts only when it holds both `.credentials.json` and `.claude.json` as regular files (a symbolic link that leads to a regular file counts; a directory, a link to a directory or a broken link in a file's place does not); the default is always listed (a launch goes there whether or not it is logged in), with `logged_in no` when a file is missing; `~/.claude` may keep its `.claude.json` in the home folder (`~/.claude.json`, where Claude Code keeps it without `CLAUDE_CONFIG_DIR`), and either place counts for it. The scan does not follow a symbolic link it finds: a linked folder under `~/.claude` or a linked `~/.claude-<name>` is no candidate. A `licenceDirs` entry is taken as given, so an entry that is itself a symbolic link to a licence folder counts. A listing is looked into for at most 200 folders (the rest counted).
- **Presence only, never content**: the tools read directory listings (`$.fs.list`) and ask `$.fs.stat` what kind each of the two paths is (a stat follows a link and opens nothing); neither file is ever opened. No credential, token or account identity can reach an answer, the debug trace or a log, and `logged_in` means only that both files are there as regular files, not that the login is valid.
- **Registry sessions** are matched by `config_dir`: the entry's path and the licence's are both normalised first (repeated separators collapsed, `.` components dropped, a trailing separator stripped; on Windows both separators, compared without case) but never resolved: `..` stays and no symbolic link is followed, so an entry recorded through a linked path counts under no discovered licence.
- **The scan is kept** 60 s in memory: a call within answers from it (the summary line says how old it is), a call after scans again; a reload of the mod forgets it.
- **The usage probe** is the host's `probeUsage` (see Host adapters): `claude -p /usage --no-session-persistence` with `CLAUDE_CONFIG_DIR` set to the licence (left out for the default directory when the orchestrator has no `CLAUDE_CONFIG_DIR` of its own, as a launch without a picker leaves it out), no shell, stdin closed, the root of the drive as cwd (`/` on Linux) so no project's files are read, at most 15 s, after which claude is killed (through the Node helper on Linux its whole process group, see Node helper). It costs no model turn and writes no transcript into the licence (`--no-session-persistence`). Of its plain text only two figures are kept, the five-hour session window and the seven-day all-models window, each as a floored percent and the reset as the CLI words it (ASCII letters, digits, blanks and `:,./()+_-` only, at most 64 characters, a word with an `@` dropped); every other line (the per-model weeks, the contributions, anything else) is discarded and the text is never returned, traced or written to disk. The reader accepts the one-line form (`Current session: 12% used · resets Oct 11, 11:20am (Europe/Budapest)`) and a form with the bar and the reset on lines of their own, percents with a fraction (floored) or `<1%` (0), and a missing window (answered as `-`). A percent must stand on its label's own line, or, in the panel form where the label line holds the label alone, on a bar line of the label's own block (up to three lines below it, before a blank line or the next label, nothing but bar characters before the percent). Ambiguous percent forms are refused with `PARSE` for the whole answer, never read as a figure: a percent over 100 however it is written (`0100%` is 100, `12345%` is refused), a negative one, any comma in the number (`1,234%` or `12,5%`), `>99%`, a number after a dot or with two dots; and, when the label's own line carries no percent, a percent on another line of the block that is no bar line (or is after a blank line), or one within 20 lines below the label (before the next label) when none stands where it may. When the label's own line does carry a percent, that percent is the answer and every later line is ignored: `Current session: 14% used` followed by a line holding `90% used` answers 14. A stray percent 21 or more lines below the label is not looked at: the window is missing (answered as `-`), not `PARSE`; if no other window is read either, the answer is one of the no-window codes (`NOT_LOGGED_IN`, `FAILED` or `PARSE`, by the text).
- **Fixed codes** when no window is read: `NO_CLAUDE` (claude cannot be started from the PATH; on the native probe, any failure to run claude other than a timeout), `TIMEOUT` (no answer within 15 s; claude was killed), `NOT_LOGGED_IN` (a login prompt or an expired credential in its output, or the cost summary the CLI prints for a config directory with no subscription login), `PARSE` (an answer with no window, empty output among them, or a window whose percent is ambiguous) and `FAILED` (a non-zero exit or an error text with no window; through the helper, any other failure to run claude). The probe never answers anything else.
- **The probe cache**: each licence's answer is kept 60 s in memory, a failed probe 15 s; a call within answers from it, with `cached yes` and its `age_seconds`. Probes run one after the other and never two at once: a call made while another call is probing probes nothing and answers from memory at once (`Another call was probing: ...`), since a wait on another call would count against the hook's own 10 s budget. The one-probe flag lives in the mod's memory: a reload of the mod while a probe runs resets it, so a call after the reload may probe while the earlier probe still runs and two probes can then run at the same time (accepted). A probe starts only while one more fits within 40 s of the call's start at its usual worst (20 s, claude's 15 s and the helper's start), and the licences left are named for the next call; a helper failure that falls back to the native probe can add up to 15 s, so such a call can run past 40 s. The engine documents no time limit for a plugin tool's call (a hook's own 10 s budget does not count the `$` calls it waits on); the 40 s are the mod's own bound.
- **How far to trust the figures**: they are what the CLI's `/usage` shows. They can be stale (up to an hour old when the CLI's own fetch fails), percents are floored and resets are as the CLI words them, truncated where it truncates them; there is no throttled class. This trade-off is accepted for the tool.
- **Not an orphan**: the probe's own process has the prompt argument `/usage` followed only by options, which the orphan rule leaves out (see Using it): it never shows as an orphan row, notice or toast.
- **Windows** (the Windows self-test runs on the development machine from WSL, through interop, against the Windows host with its PowerShell and `node.exe`; no claude session has run on Windows): the probe runs `claude.exe` from the PATH without a shell, through the Node helper or natively, in the root of the temporary folder's drive through the helper and of the profile folder's drive natively; an npm `claude.cmd` shim is not run (no shell) and answers `NO_CLAUDE`. `windows-selftest.py` proves the helper's lookup of `claude.exe` on a PATH without a shell, and the `NO_CLAUDE` answers, with a copy of `node.exe` standing in for claude; no claude session was started on Windows. The discovery's Windows path forms are covered by mock tests only.

### Node ports of the tests

Node.js is the mod's single runtime outside the engine, also for the self-tests and the end-to-end scripts, so that they run the same on Linux, WSL, macOS and Windows. Each Python self-test and each shell end-to-end script therefore has a Node port beside it, run with `node mod/tests/<name>.mjs` from any directory, with Node 22 or newer and nothing but its standard library:

- `probe-selftest.mjs`, the port of `probe-selftest.py`; `windows-selftest.mjs`, the port of `windows-selftest.py`. What they share (Python's string literals, `json.dumps`, `splitlines`, equality and the like, written out) is in `lib/selftest.mjs`.
- `e2e-smoke.mjs`, `e2e-tools.mjs`, `e2e-write-tools.mjs`, `e2e-stop.mjs`, `e2e-guard.mjs`, `e2e-digest.mjs`, `e2e-lint.mjs` and `e2e-licences.mjs`, the ports of the eight `e2e-*.sh` scripts. What they share (the check lines, the scratch directory and its cleanup, the orchestrator's start and wait, the transcript reading, the process checks) is in `lib/e2e.mjs`.
- `run-all.mjs` runs `helper.test.mjs` (under `node --test`), `probe-selftest.mjs` and `windows-selftest.mjs` one after the other and prints a summary; it runs no end-to-end script, since each of those starts real `claude` sessions and spends quota.

The Python and shell versions stay beside the ports. Neither side is authoritative: a port checks what its twin checks, with the same fixtures, the same options and variables (`KEEP_TRACE`, `KEEP_OUT`, `HIDE_NODE`, `E2E_MAIN_DIR`, `E2E_IDENTITY`, `SC_WIN_SCRATCH`, `SC_WIN_NODE`), the same cost caps and time limits, the same scratch directories and cleanup, and the same `ok`, `FAIL`, `skip` and `info` lines, so the two must agree, and a difference between them is a bug in one of them. Where a shell script reads a file with `jq`, its port reads it as `jq` does (`jqPick`, `jqLastTruthy`, `jsonValues` and `resultText` in `lib/e2e.mjs`): every registry entry with a title, not only the last; a tool answer without `content`, or with a `content` that is no string and no list, as no answer; a file that holds anything but JSON values, or none, as a failure. A pair is compared by running both on the same machine, `sh mod/tests/e2e-<name>.sh` and `node mod/tests/e2e-<name>.mjs` (each starts its own sessions and spends quota), and comparing their `ok`, `FAIL` and `skip` lines; a line that depends on the model or on the machine's other processes, such as `no other tool was called` in the digest test, can differ between two runs of the same script. The shell scripts run on Linux and WSL (`e2e-smoke.sh` also under Git Bash); the pairs are compared on Linux and WSL only, and the Windows paths of the ports are described below.

The end-to-end ports need no `sh`, `grep`, `tr`, `sed`, `jq` or `cygpath`. The orchestrator's foreground waits run small node scripts of the test, by the absolute path of the node that runs the test, so `HIDE_NODE=1` still hides Node from the mod. The smoke test's interactive part runs where `tmux` exists (the pane runs a node script, no shell) and prints `skip` elsewhere. The `/proc` checks run on Linux only and print `skip` elsewhere; `e2e-stop.mjs` needs `/proc` throughout and fails at once without it, as `e2e-stop.sh` does. Only a run's own processes are ever signalled. At its end each script, in both versions, checks that no process other than itself and its parent (left out by pid, never by a name) has the scratch directory in its command line or, where `/proc` lists it, its working directory, so a worker, a shell or a `sleep` of the run that is still there is reported. The guard and lint tests still tell the orchestrator to run `git branch -D`, `cat`, `jq`, a heredoc and `git push --force` through its Bash tool, because those commands are what the guards are tested on (on Windows the `jq` step needs `jq` on Git Bash's PATH). `e2e-write-tools.mjs` makes symbolic links, as its twin does.

Where a port does more than its twin: the self-test ports remove every scratch directory they make (`probe-selftest.py` leaves four under the temporary folder); `e2e-smoke.mjs` checks that every trace line is JSON without `jq` (the shell script skips that check where `jq` is missing). Where it does otherwise: the write-tools port's wait script finds the registry and the runs directory beside itself rather than on its command line. The wait scripts of the licences, lint, stop and write-tools ports import `lib/e2e.mjs` by its absolute URL, to read the registry as their twins' `jq` does.

Windows: `windows-selftest.mjs` runs from WSL through interop and `wslpath`, as the Python version does, and where `process.platform` is `win32` it starts `powershell.exe`, `cmd.exe`, Git Bash's `bash.exe` and `node.exe` directly and takes Windows paths as they are. That native branch has not been run on a Windows host. The same holds for the Windows paths of the end-to-end ports (no `/proc`, the process list through `Win32_Process`, `claude.exe` found on the PATH, a `claude.cmd` shim refused because Node starts none without a shell, `CLAUDE_CODE_GIT_BASH_PATH` set from the Git on the PATH): they have been run on Linux (WSL) only.

After a change to the mod, run the validation and the tests before relying on it.

## Host adapters

Everything the mod does that differs per operating system, or needs a process, goes through one interface, `Host` in `mod/hooks/host.ts`, with two adapters: `host-posix.ts` (Linux and WSL: `sh`, `mv`, `rm`, `tail`, `mkdir`, `sleep`, `/proc`) and `host-windows.ts` (native Windows: Windows PowerShell 5.1 scripts run with `-File`, paths in the `C:/...` form). `selectHost` in `host.ts` is the one platform choice: `OS=Windows_NT` with a drive-letter `USERPROFILE` takes the Windows adapter, anything else the Linux one. `register.tsx` calls it once per load (again after a failed choice) and reads the chosen adapter's `platform` only where an answer's wording or a path rule differs. Each adapter's scripts sit in its own file; operations both do alike with `$.fs` and plain TypeScript are in `host-shared.ts`.

An adapter never holds `$` (the validator follows `$` only into functions of `register.tsx`): it gets a `HostPort`, the engine facilities `register.tsx` builds over the hook's `$` (`run` and `write`, traced; `read`, `readBytes` (optional: a file's bytes, for the native drift hash), `exists`, `stat`, `list`, `now`, `sleep`, `env` for `HOME`, `USERPROFILE` and `SystemRoot`; the runs directory; `traceError`; `noteDirectWrite`, the once-per-load toast; `noteHelper`, the Node helper's detection and fallbacks). With the `helper` option at `auto` the chosen adapter is wrapped by `withHelper` (`host-helper.ts`, see Node helper).

## Node helper

`mod/helper/host.mjs` (with `protocol.mjs`, `ops.mjs`, `files.mjs`, `linux.mjs`, `stop.mjs` and `usage.mjs`) does the host operations the engine's `$.fs` lacks in one Node.js process per call: Node 22 or newer, standard library only, no build step. The mod finds it under its own folder (`$.plugin.root`). Its protocol:

1. The mod runs `node <plugin>/helper/host.mjs <op>` by argv, no shell, with one JSON request on stdin.
2. The helper prints one JSON object: `{"ok":true,...}` with the answer's fields, or `{"ok":false,"code":"<CODE>"}`, and exits 0 or 1.
3. Codes are fixed words (`BAD_OP`, `BAD_REQUEST`, `TOO_LARGE`, `UNSUPPORTED`, `NOT_FOUND`, `ACCESS`, `BUSY`, `EXISTS`, `IS_DIR`, `NOT_DIR`, `IS_LINK`, `NOT_FILE`, `NO_SPACE`, `READ_ONLY`, `CROSS_DEVICE`, `IO`, `INTERNAL`, and the usage probe's own `NO_CLAUDE`, `TIMEOUT`, `NOT_LOGGED_IN`, `PARSE`, `FAILED`): no Node error message, path or file content is ever part of an answer.
4. Operations: `processTree` and `stopProcesses` (Linux only, like the probe, and never in a batch: the tree and the stop of `stop_worker`, printed as `TREE_SCRIPT` and `STOP_SCRIPT` print them; signals by `process.kill`, the waits inside the helper; always the live `/proc`, never the probe's test tree: `SC_HELPER_PROC_ROOT` is ignored here, since a fake tree's pids would be signalled on the real machine), `probe` (Linux: `/proc` read natively, printed as `PROBE_SCRIPT` prints it, `CLAUDE_CONFIG_DIR` the only value taken from a process environment, `procStart` and `sessionId` the only fields taken from a sessions file), `writeAtomic`, `renameOver`, `removeFile` (`{path, regularOnly?}`: with `regularOnly` a symbolic link, or on Windows a junction, is refused with `IS_LINK` and a non-file with `NOT_FILE`, by `lstat`, and nothing is removed), `append` (one write on an append descriptor), `tail` (the last 600 lines from the end of the file, each cut to 20000 characters, or the lines and width asked, the answer kept under the engine's 4 MiB output cap by leaving out the oldest lines), `rotate`, `filesNewerThan` (read-only: `{dir, since, max}` answers `{files: [{path, mtimeMs}], total}`, a walk by `lstat` that never follows a symbolic link or, on Windows, a junction out of the tree, passes over a folder it cannot read and never enters `.git`), `hashTree` (read-only: `{root, dirs, files}` answers `{files: [{path, sha256}], total}` for the regular files directly in each folder of `dirs` and each file of `files`, relative to `root`, sorted; every entry by `lstat`, so no symbolic link or junction inside the root is followed or hashed, a folder within a folder of `dirs` is passed over, a folder or file not there counts as empty or absent; SHA-256 over the bytes with each CRLF folded to LF, a file with a NUL byte as it is; at most 500 files and 8 MiB per file, else `TOO_LARGE`; at most 20 entries per list, and an absolute path or a relative path with `.`, `..`, an empty part or a drive is `BAD_REQUEST`).
5. `batch` runs a list of file operations in order in one process and stops at the first failure, answering its position.
6. `probeUsage` (`usage.mjs`, both platforms, never in a batch): `{configDir, isInherited?}` runs `claude -p /usage --no-session-persistence` (`claude.exe` on Windows) found on the PATH without a shell, with `CLAUDE_CONFIG_DIR` set (removed when `isInherited`), stdin closed, the root of the temporary folder's drive as cwd, a 15 s timeout and at most 1 MiB each of stdout and stderr kept in memory. On Linux claude runs detached, as the leader of a process group of its own, and the whole group gets SIGKILL (the negative pid) only in three cases: on the timeout, on an output past 1 MiB, or when its output pipe is still open 500 ms after claude exited. A process claude started that closed its output and error pipes and lingers after a clean exit is not killed and survives the probe, and one that left the group with a setsid of its own is out of reach in all three cases; on Windows claude alone is killed (SIGKILL through spawnSync). It answers `{five, seven}` (each `{percent, resets}` or null) or one of its five codes (`BAD_REQUEST` for a request without an absolute `configDir`); the text is never written or returned. `SC_HELPER_USAGE_TIMEOUT_MS` shortens the timeout for the helper's own tests only together with `SC_HELPER_TEST=1`.

`withHelper` in `mod/hooks/host-helper.ts` puts the helper in front of the chosen adapter. For `stopProcessTree` on Linux it lists the tree with `processTree` (a failure there leaves the whole stop to the adapter, which lists itself) and stops it with `stopProcesses` (timeout 45 s); a stop that fails falls back to `STOP_SCRIPT` over the same listing, which signals only a process that still has its listed start, and the report's `Note:` says so (after a timeout also that signals the helper sent before it was cut off are not in the record); the Abort check after the stop decides what `stop_worker` says. On Windows the stop stays on `TREE_PS1` and `taskkill.exe` (Node's standard library cannot list processes). Node is looked for at the first operation that needs it (`node --version`, untraced): without Node, or with one older than 22, the adapter's own operations run, with a `helper` trace line and no error. While no usable Node was found, the first helper-needing operation 10 minutes or more after the last lookup looks again, so a Node installed meanwhile is taken without a reload; operations at the same moment share one lookup, and a Node once found stays for the load. The `helper` trace line is written once per change of state (not found, too old, found), not at every lookup. A call that fails (Node cannot start or times out, its output is cut, is not one JSON object, or answers `ok:false`) falls back to the adapter's own operation for that call: the trace gets a `helper.fallback` line with the operation and the code (for the trace's own write, once per operation and load), and the first fallback of the load raises one toast (`helper fallback: <op>`). The one exception is an append (a log line, or the trace's own rotate-and-append batch) that timed out: the helper may have written it already, so it is not made again. Its `helper.fallback` line carries `isRepeated: false`, the toast reads `helper fallback: append (timed out, not repeated)`, and the lines may be missing from the log but are never in it twice. Every other failure of an append (Node not starting, an exit code with no answer, an answer that is not JSON, `ok:false`) means nothing was written, and the adapter appends. On Windows the process probe stays `PROBE_PS1` (Node's standard library cannot list processes) and a transcript under the read cap is still read in the engine; the helper replaces the PowerShell file script. The trace's own write goes as one batch (rotation, then append). The built-in adapters stay as the fallback.

Cost measured on the machines it targets (medians: of 100 runs on Linux; on Windows of 20 single operations, 5 batches and one tail, timed from WSL through interop):

| --- | --- | --- | --- |

## PowerShell launch route

On native Windows the engine offers its Bash tool only when it finds Git Bash. With the `launchRoute` option at `powershell`, `launch_worker` starts the worker through the engine's PowerShell tool instead (PowerShell 7 or Windows PowerShell 5.1, whichever the tool runs; the engine offers that tool by default only when it does not find Git Bash, otherwise with `CLAUDE_CODE_USE_POWERSHELL_TOOL=1`). The default, `bash`, is the route described above, unchanged; on Linux and WSL the option changes nothing. `hooks/host-powershell.ts` builds the command; for a fresh launch with a picked config directory it reads:

```powershell
$env:PSModulePath = "$PSHOME\Modules"
$ErrorActionPreference = 'Stop'
$env:CLAUDE_CODE_EFFORT_LEVEL = 'high'
$env:CLAUDE_CONFIG_DIR = 'C:/Users/u/.claude/lic-b'
$exe = (Get-Command claude.exe -ErrorAction Stop).Source
$p = Start-Process -FilePath $exe -ArgumentList '-p --model opus -n w-fix-the-parser-261010143117 --settings "{\"crossSessionInbound\":\"accept\"}" --dangerously-skip-permissions --output-format json' -WorkingDirectory 'C:/work/my project' -RedirectStandardInput 'C:/Users/u/scratch/prompt.md' -RedirectStandardOutput 'C:/Users/u/.claude/session-control/runs/20261010143117-fix-the-parser.json' -RedirectStandardError 'C:/Users/u/.claude/session-control/runs/20261010143117-fix-the-parser.err' -NoNewWindow -PassThru
$null = $p.Handle
Set-Content -LiteralPath 'C:/Users/u/.claude/session-control/runs/20261010143117-fix-the-parser.pid' -Value $p.Id -Encoding Ascii
$p.WaitForExit()
exit $p.ExitCode
```

- **Flags**: those of the Bash route, in its order (`--resume <session id>` right after the model for a resume), with no prompt argument: the prompt reaches `claude.exe` on standard input from the prompt file, so it never meets the command-line length limit and no PowerShell encoding touches it. The result and error files are `claude.exe`'s own standard output and error (Start-Process's redirections: the bytes go through as written). `CLAUDE_CONFIG_DIR` is set only when the worker does not inherit the config directory, as on the Bash route.
- **Quoting**: Windows PowerShell 5.1 joins Start-Process's argument list with blanks and quotes nothing, so the arguments go as one string, each quoted by the C runtime's command-line rules that `claude.exe` parses with: a plain word stays as it is (so the probe still finds `--model opus`), anything with a blank or a double quote goes in double quotes with its quotes, and the backslashes before them, escaped. The `--settings` JSON thus arrives as one argument under 5.1 and 7 alike. Every value then sits in a PowerShell literal that keeps the whole command in printable ASCII: single-quoted with its quotes doubled, or, for a value with other characters (a user folder `José`), double-quoted with `$([char]0x....)` for each of them, so the command reads the same whatever encoding the tool hands it on in.
- **Wildcards**: Start-Process reads `-WorkingDirectory` and its redirection paths as wildcard patterns. The launch directory is escaped (each `[`, `]`, `*`, `?` and backtick behind a backtick), which both versions read back as the path. No spelling of a redirection path with `[`, `]` or a backtick reaches both versions (plain, the pattern finds no file; escaped, PowerShell 7 looks for the backticks themselves, and 5.1 does for standard input), so on this route a prompt file or runs directory holding one of them is refused before anything runs, with a message naming the path.
- **Refusal without the tool**: when the session has no PowerShell tool the launch is refused (`the worker could not be started through the PowerShell tool (...); nothing was launched.`) with the hint to start the orchestrator with `CLAUDE_CODE_USE_POWERSHELL_TOOL=1` or to set the option back to `bash`; there is no silent fall back to the Bash tool.
- **Pid**: the launch guards and the pid discovery are the Windows adapter's, unchanged. The command writes `claude.exe`'s pid to `<runs>/<stamp>-<slug>.pid`; after discovery the mod reads it as one more fact: the `worker.found` trace line says whether it matches the probe's pid (`same`, `differs`, `unread`), and the answer names it when it differs. The registry takes the probe's pid either way.
- **Exit**: the command waits for `claude.exe` and exits with its exit code, so the tool's background exit notification carries it.

Verified on the Windows host (Windows PowerShell 5.1.22621, PowerShell 7.6.6), from WSL, with `mod/tests/windows-selftest.py`. It renders the command with the real `powershellLaunchCommand` and runs it as a script under both versions, with `node.exe` and a stub script standing in for `claude.exe`. Three layouts ran under each version: a fresh launch inheriting the config directory, with blanks and a quote in its paths; a picked config directory with brackets, a backtick and non-ASCII letters in the launch directory; and a resume. In each run:
- the argv arrived intact, the name and the settings JSON as single arguments;
- the prompt arrived byte for byte, including non-ASCII text, quotes and CRLF and LF line ends;
- the result file was UTF-8 with no BOM;
- the pid file held the child's pid;
- the exit code came back (0, 3 and 1);
- the working directory was right;
- `CLAUDE_CONFIG_DIR` was inherited or set as asked.

A prompt file under a bracketed folder failed at Start-Process under both versions, as the refusal says. The mocked tests cover the command text (with and without a picker, a resume, blanks and quotes in paths, a title with quotes), the option on Windows and on Linux, and the refusals.

Not verified live: no Windows claude session has been started through this route. An earlier scratch variant of this command (the same Start-Process shape, without `-n` and `--settings`) did run one live haiku worker through the PowerShell tool, a fresh launch with a plain ASCII layout. Still unproven live:
- a resume, whose prompt also arrives on standard input;
- non-ASCII or bracketed launch directories;
- the way the tool itself hands the command to PowerShell (the dry runs ran it as a `-File` script);
- whether stopping the background task, or its time limit, also ends the `claude.exe` that Start-Process started.
